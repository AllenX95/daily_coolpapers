# Daily Cool Papers PRD：投资业务优化

- 文档状态：Draft v0.4（Top 5 需求已确认，外部信号与自动趋势发现延期）
- 创建日期：2026-08-30
- 最后更新：2026-09-04
- 文档定位：在现有 MVP 上，把论文阅读工具升级为个人 AI 投资情报工作台
- 面向版本：下一轮及后续分阶段改造
- 主要读者：产品负责人、开发者、测试与后续代码审查者

## 1. 产品结论

Daily Cool Papers 的核心价值不应停留在“少读一些论文”，而应形成一条连续的个人投资研究链路：

```text
稳定获得每日论文
  → 用用户定义的关注方向做轻量分类
  → 只对匹配或可能匹配的论文自动做摘要评估
  → 对少量论文做全文评估
  → 人工形成收藏、跳过和投资主题判断
  → 对值得持续关注的作者与机构建立跟踪对象
  → 基于用户确认的收藏论文生成有证据回链的研究备忘录
  → 逐步沉淀技术趋势和投资方向
```

本 PRD 采用“先可靠、再沉淀、后增强”的产品策略：

1. **先建立可靠输入**：抓取后自动完成摘要评估，并提供可定位问题的细粒度日志。
2. **再让用户定义筛选边界**：由用户创建关注方向，LLM 只执行分类，不自动发明方向；匹配结果决定是否自动摘要评估。
3. **再记录人工判断**：只在成功完成全文评估后提供收藏、跳过和加入投资主题操作。
4. **再建立研究对象**：以手工确认为主，记录第一作者和机构/企业，避免首版依赖不稳定的 PDF 机构识别和实体消歧。
5. **再形成投资输出**：由用户选择一个关注方向、一个投资主题或手工选择收藏论文，生成可回链到论文证据的投资主题研究备忘录。
6. **外部增强后置**：外部学术、开源、商业和融资信号、自动趋势发现与自动机构识别不进入本版，后续单独立项。

## 2. 目标用户与核心工作

目标用户是以中国市场为主要工作环境、重点关注 AI 的 VC 投资人。用户的日常任务不是完整追踪所有论文，而是：

- 从每天新增的论文中识别值得全文阅读的少数项目；
- 判断某项技术是否可能形成新产品、新公司或产业链机会；
- 把一次阅读形成的判断沉淀到长期投资主题中；
- 记住值得持续关注的研究者、实验室和公司；
- 随时间观察某个主题、团队和技术路线是否持续增强。

## 3. 总体目标与非目标

### 3.1 总体目标

1. 每日抓取与摘要评估成为无需人工补操作的可靠流水线。
2. 用户可以用自然语言定义关注方向，把自动摘要评估限制在匹配或可能匹配的论文范围内。
3. 用户只需对少量成功完成全文评估的论文作出简单、明确的后续判断。
4. 收藏、跳过、投资主题和团队跟踪成为可查询、可维护的本地结构化数据。
5. 所有新能力保持本地单用户、轻量、可迁移、可测试，不引入账号和云端协作。
6. 为后续趋势分析和团队情报积累干净的人工标注数据，但首版不做复杂推荐系统。
7. 用户能够把一组已收藏论文及其内部评估结果沉淀为可追溯、可版本化、可补充个人判断的投资主题研究备忘录。

### 3.2 总体非目标

- 不做多人协作、权限系统或云端同步。
- 不在首版自动抽取 PDF 中的机构，也不自动判断作者当前任职信息。
- 不在首版做跨来源人物/机构实体消歧、自动合并或知识图谱。
- 不在首版做嵌套投资主题、复杂标签体系或由模型自动归档。
- 不由模型自动发明关注方向，也不在首版自动发现未知技术趋势。
- 不在本版接入新的外部学术、开源、融资、公司或市场信号；研究备忘录不得假装已经完成外部事实核验。
- 不自动定时生成研究备忘录，不由系统代替用户作出投资决策。
- 不在未确认投资判断前自动对外发送邮件、微信或飞书通知。
- 不把“社区欢迎度”直接等同于“投资价值”；社区信号只用于降低阅读量。

## 4. 优先级与版本范围

| 优先级 | 模块 | 当前决策 | 交付边界 |
|---|---|---|---|
| P0 | 每日情报自动化与细粒度日志 | 已确认 | 抓取、完整性校验、入库、缺失摘要评估、结构化事件和任务状态闭环 |
| P1 | 全文评估后的个人整理 | 已确认 | 收藏/跳过、投资主题 CRUD、论文与主题的手动多对多归档 |
| P1 | 手动团队跟踪 | 已确认 | 手动确认第一作者和机构/企业，建立作者库、机构库和论文跟踪关系 |
| P2 | 用户定义关注方向的自动筛选与增量分类 | 已确认 | 轻量分类、摘要评估门控、人工确认和指定时间段历史补分类 |
| P2 | 投资主题研究备忘录 | 已确认 | 两种选论文模式、内部证据综合、版本化 AI 草稿、个人投资判断和 Markdown 导出 |

P0、两个 P1、关注方向和研究备忘录模块可以分别开发和验收。P1 依赖现有成功全文评估记录，但不依赖 P0 新流水线先上线；关注方向模块在上线后改变 P0 的摘要候选规则，但不应阻塞 P0 先完成基础流水线。研究备忘录依赖模块 B 的收藏语义；按关注方向预选时依赖模块 D，按投资主题预选时依赖模块 B；模块 C 的人工团队数据是可选增强，不应成为生成前置条件。

## 5. 统一产品规则

### 5.1 论文状态分层

系统必须区分五类含义，不能继续混用：

1. **处理状态**：是否已有成功的摘要评估或全文评估。
2. **关注方向分类**：模型是否认为论文匹配用户定义的阅读前筛选方向，以及用户是否确认或否决。
3. **个人决策**：未处理、收藏或跳过。
4. **研究归档**：属于哪些投资主题，以及是否跟踪其团队。
5. **研究输出**：基于用户确认的论文与评估快照生成的研究备忘录版本，以及用户另行维护的个人投资判断。

匹配关注方向不等于加入投资主题；成功完成全文评估不等于收藏；加入投资主题不等于收藏；跟踪团队也不要求论文处于收藏状态。备忘录中的论文集合以生成前用户最终确认的快照为准，后续取消收藏、调整分类或改变主题关系不得静默改写历史备忘录。

### 5.2 首版交互原则

- 模型可以按用户定义的关注方向自动分类并执行已授权的摘要/全文评估；关注方向定义、`possible` 的正式分类、人工否决、投资主题归档和团队跟踪仍由用户决定。
- 研究备忘录只能由用户明确触发；模型生成的内容与用户编辑的“我的投资判断”分开保存，重新生成不得覆盖旧版本。
- 同一操作重复提交必须幂等，不得产生重复主题关系或重复团队跟踪记录。
- 删除优先使用“取消关系”或“归档”，避免不可恢复地删除历史研究数据。
- 所有状态变更使用 POST、CSRF 和现有同源跳转防护。
- 新表使用向前兼容的 SQLite migration；不改写现有论文与评估历史。

### 5.3 统一全文资格判定

模块 B 和模块 C 中**以论文为目标的写操作**统一使用以下资格条件，包括个人决策、论文主题关系和论文团队跟踪。投资主题 CRUD、作者 CRUD、机构 CRUD 不受全文资格限制：

```sql
EXISTS (
  SELECT 1 FROM evaluations
  WHERE paper_id = ?
    AND evaluation_type = 'fulltext_review'
    AND status = 'success'
)
```

资格取决于**历史中是否存在任意一次成功全文评估**，不是“最新一次评估必须成功”。因此最新一次全文评估失败、但历史中有成功记录的论文，仍可收藏、跳过、加入主题或跟踪团队。详情页展示和所有写接口必须复用同一数据库资格函数。

模块 E 的备忘录候选只来自当前处于“收藏”状态的论文，因此间接继承上述全文资格。用户确认生成时，系统为每篇论文锁定当时最新一次成功全文评估；摘要评估允许为空，存在时锁定当时最新一次成功结果。历史备忘录始终读取已锁定的评估与输入快照，不跟随“最新结果”漂移。

## 模块 A：每日情报自动化与细粒度日志（P0）

### A1. 背景

Daily Cool Papers 当前已经分别具备 papers.cool 抓取、摘要级 LLM 评估、后台任务、任务进度和运行日志能力，但抓取与摘要评估仍是两个独立步骤。

现有定时调度只创建抓取和缓存清理任务；手工操作也需要先点击“抓取最新 Metadata”，再点击“评估缺失摘要”。这与主 PRD 和 README 中“每日抓取后自动完成摘要评估”的产品预期不一致，也使每日论文筛选依赖人工补操作。

另一方面，当前抓取日志主要回答“任务成功或失败”，不足以回答以下排障问题：

- 哪个日期、哪个类目没有抓到数据？
- HTTP 请求成功后，HTML 是否正常解析？
- 页面声称有多少篇论文，系统实际解析、写入了多少篇？
- 哪些论文是新增、更新、重复或因字段问题被跳过？
- 本次抓取计划评估多少篇，最终成功、失败、跳过多少篇？
- 某次摘要评估失败属于抓取问题、配置问题、Provider 问题还是模型输出问题？

因此，本轮需要把抓取、完整性检查和摘要评估收敛为一条可自动执行、可追踪、可恢复的每日情报流水线。

### A2. 产品结论

本轮采用以下产品定义：

> 一次“每日情报流水线”必须覆盖抓取、数据完整性检查、入库和缺失摘要评估。只有所有可执行阶段都到达确定终态后，该次流水线才算结束。

流水线允许部分成功。例如某个类目抓取失败时，其他成功类目的论文仍应入库并继续摘要评估，但整次流水线状态必须显示为“部分成功”，不能被标记成完全成功。

### A3. 目标

#### A3.1 业务目标

1. 用户无需在抓取后再次手工启动摘要评估。
2. 每次定时或手工运行都能明确看到抓取和摘要评估两个阶段的状态。
3. 当数据缺失、页面结构变化或 LLM 失败时，用户能快速定位到具体日期、类目、论文和失败阶段。
4. 重复运行不会为同一论文创建不必要的重复摘要评估。
5. 单一类目或单篇论文失败不阻塞其他可继续处理的对象。

#### A3.2 工程目标

1. 保持现有 Flask 路由、服务、数据库和 JobRunner 分层，不为本轮引入新的基础设施服务。
2. 继续使用 SQLite 作为任务状态和结构化事件的事实来源。
3. 网络请求保持可注入、可 mock，测试不依赖真实 papers.cool 或真实 LLM。
4. 所有任务必须具有稳定的关联 ID，能够串联抓取、入库和评估日志。

### A4. 模块非目标

以下内容不属于本轮范围：

- 自动执行全文评估或自动下载 PDF。
- 新增 OpenAlex、Semantic Scholar、Hugging Face、GitHub 等外部数据源。
- 个性化推荐、兴趣画像和反馈学习。
- 收藏、投资主题和团队跟踪；这些能力分别由模块 B、模块 C 定义，不纳入 P0 流水线实施范围。
- 修改 LLM 的 VC 评分框架或增加新的投资字段。
- 邮件、微信、飞书或其他外部通知。
- 将本地任务队列改造成分布式任务系统。

### A5. 术语与状态

#### A5.1 术语

- **流水线运行（Pipeline Run）**：一次由定时器或用户触发的完整“抓取 → 校验 → 入库 → 摘要评估”过程。
- **抓取单元（Crawl Unit）**：一个确定的 `抓取日期 × 类目` 组合。
- **结构化事件（Job Event）**：保存在 SQLite 中、可查询和统计的任务事件。
- **运行日志（Runtime Log）**：写入 `logs/current.log`、供人工阅读和排障的文本日志。
- **摘要评估候选**：本轮成功抓取并入库，且按本 PRD 规则需要执行摘要评估的论文。
- **关注方向分类阶段**：模块 D 上线后位于入库和摘要评估之间的可选阶段；有启用方向时执行分类，无启用方向时合法跳过。

#### A5.2 流水线状态

- `pending`：已创建，尚未开始。
- `running`：至少一个阶段正在执行。
- `success`：全部应执行阶段成功，允许存在明确记录的非错误跳过。
- `partial_success`：部分抓取单元或部分摘要评估失败，但其余对象已完成。
- `failed`：没有形成可用结果，或发生阻止后续阶段执行的系统级错误。
- `interrupted`：服务退出或重启导致运行未正常结束。

最终状态按以下优先级计算：

| 条件 | 流水线状态 |
|---|---|
| 所有抓取单元均为 `success/empty_success`，且所有应执行摘要评估均成功或被非错误跳过 | `success` |
| 至少获得一个可用抓取结果，但存在任一 `warning/failed` 抓取单元或任一摘要评估失败 | `partial_success` |
| 所有抓取单元均为合法 `empty_success`，没有摘要候选 | `success` |
| 没有获得任何可用结果，且至少一个抓取单元失败 | `failed` |
| 计划、数据库或配置等系统级错误导致无法继续任何后续阶段 | `failed` |
| 服务退出或重启时任务尚未进入终态 | `interrupted` |

非错误跳过仅包括已有成功评估、已有兼容评估正在执行，以及本 PRD 明确定义的输入不完整跳过。`warning` 不得汇总为完全成功。

#### A5.3 抓取单元状态

- `success`：抓取、解析和入库均通过完整性检查。
- `empty_success`：页面明确声明该日期和类目没有论文，系统确认这是合法空结果。
- `warning`：获得了部分可用数据，但完整性无法完全确认。
- `failed`：网络、页面日期、解析、完整性或数据库阶段失败。

### A6. 目标用户流程

#### A6.1 定时运行

所有计划日期使用 `Asia/Shanghai` 时区计算；结构化事件时间使用带时区的 ISO 8601 UTC 时间保存，UI 转换为 `Asia/Shanghai` 展示。

“最新”不是简单取自然日当天，而是复用现有 arXiv 可用日期规则计算 `latest_available_arxiv_date`。流水线创建时必须固化以下计划快照，运行过程中配置变化不影响本次任务：

- 触发来源和目标日期或日期范围；
- 启用类目的 ID、类目名、top_n 和 sort 参数；
- 摘要 Prompt、LLM Profile 和并发配置的标识；
- 模块 D 上线后，启用关注方向、分类 Prompt、分类 Profile 和模型配置的快照；
- 计划生成时间和应用时区。

```text
到达配置时间
  → 创建每日情报流水线
  → 生成本次日期和启用类目计划
  → 并发执行各抓取单元
  → 对每个抓取单元做完整性检查
  → 保存成功或可用的论文
  → [模块 D 上线后] 按启用中的关注方向执行轻量分类
  → 汇总并去重摘要评估候选
  → 自动执行缺失摘要评估
  → 计算 success / partial_success / failed
  → 在任务中心和日志页展示结果
```

#### A6.2 手工运行

首页原“抓取最新 Metadata”主操作调整为“抓取并摘要评估”。用户提交后立即看到一个流水线任务，而不是两个彼此独立的任务。

“补抓到最新”也必须在每个成功补抓日期后执行候选汇总，并在补抓计划结束后完成所有缺失摘要评估。

现有“评估缺失摘要”保留，作为历史数据修复和失败重试入口，不再是正常每日流程的必需步骤。

补抓范围从数据库中最后一个已完成日期的下一个可用 arXiv 日期开始，到触发时计算出的 `latest_available_arxiv_date` 结束。用户显式提交起止日期时，以显式范围为准，但仍需跳过周末和已知 arXiv 非更新日。

### A7. 功能需求

#### A7.1 流水线编排

1. 定时器必须创建完整流水线，不再只创建裸 `crawl` 任务。
2. 手工“抓取并摘要评估”和“补抓到最新”必须进入相同的流水线状态模型。
3. 抓取阶段结束后，无需用户确认，自动进入摘要候选选择；模块 D 未上线或没有启用关注方向时处理全部合格候选，有启用方向时先分类再进入摘要评估。
4. 抓取失败的类目不得阻止成功类目的论文进入摘要评估。
5. 摘要评估阶段必须复用现有 `llm.abstract_concurrency` 设置。
6. 流水线必须记录触发来源：`scheduled`、`manual_latest` 或 `manual_catch_up`。
7. P0 阶段同一时间只允许一个包含抓取阶段的流水线处于 `pending/running`。重复触发不创建新任务，UI 跳转到现有任务并说明原因。
8. 流水线 payload 必须保存目标日期范围和类目配置快照；该快照是重试、日志和验收的唯一计划依据。
9. 模块 D 上线后，方向分类成为主流水线的正式阶段：有启用方向时必须到达成功、部分成功或失败终态；无启用方向时产生合法跳过事件后继续摘要评估。
10. 分类失败和摘要评估失败分别汇总；分类失败不得被后续成功摘要评估覆盖，摘要评估失败也不得改写分类结果。

#### A7.2 摘要评估候选规则

模块 D 未上线，或没有任何启用中的关注方向时，默认只自动评估满足以下条件的论文：

1. 本轮至少出现在一个成功或 warning 的抓取单元中；
2. 具有规范化基础 arXiv ID，标题和 Abstract 均为非空文本；
3. 当前不存在成功的 `abstract_review`；
4. 当前不存在同一论文正在排队或运行的摘要评估。

补充规则：

- 同一论文出现在多个类目时，本轮只自动评估一次。
- 抓取解析时必须去除 arXiv 版本后缀，使用规范化基础 `arxiv_id` 完成论文 upsert；入库后以本地 `paper_id` 作为候选去重、评估状态查询和并发锁定键。
- 摘要评估并发锁的逻辑唯一键为 `(paper_id, evaluation_type='abstract_review')`。
- Rank、PDF 点击数、Kimi 点击数或 Reading Stars 变化不自动触发重新评估。
- 标题或 Abstract 更新后是否重新评估，本轮默认不自动触发；保留用户手工重新评估入口。
- 用户显式使用“评估缺失摘要”时，仍遵循去重和正在运行检查。

模块 D 上线且至少存在一个启用中的关注方向时，本节规则增加一项门控条件：只有分类结果为 `matched` 或 `possible` 的论文自动进入摘要评估；`unmatched`、最终 `failed` 不自动进入。用户对 `unmatched` 论文发起的单篇手动摘要评估属于明确绕过自动门控，但仍遵循已有成功结果和正在运行检查。详细状态、人工确认和历史补分类规则以模块 D 为准。

#### A7.3 抓取完整性检查

每个抓取单元必须分别完成以下检查：

1. HTTP 请求是否成功，最终 URL 是否仍为允许的 papers.cool 页面。
2. 页面日期是否与目标日期一致；无法确认时记录 warning。
3. 页面声明的总论文数是否可解析。
4. 预期返回数按 `min(类目 top_n, 页面声明总数)` 计算。
5. 实际解析数、具有 arXiv ID 的数量和成功入库数量必须分别记录。
6. 判定顺序必须是：HTTP 和最终 URL → 页面日期 → 页面声明总数 → 实际解析数 → 字段完整性 → 入库结果。前序硬失败不得被后续空结果覆盖。
7. 只有 HTTP、最终 URL 和页面日期校验通过，且页面明确声明总数为 0 时，才可以判定为 empty_success。
8. 页面声明总数大于 0、但解析数为 0 时必须判定为 failed。
9. 无法解析页面总数且解析数为 0 时必须判定为 failed，并记录 `declared_total_unknown` 和 `parse_zero_without_total`。
10. 无法解析页面总数但解析出有效论文时，可以继续入库，但状态为 warning，并记录 `declared_total_unknown`。
11. 关键字段缺失率超过配置阈值时状态至少为 warning；arXiv ID 缺失的条目不得入库。
12. 不得仅根据 HTTP 200 将抓取单元判定为成功。

#### A7.4 失败隔离与恢复

1. 网络请求继续使用现有超时与重试策略，每次尝试都必须产生事件。
2. 一个类目失败后继续处理其他类目。
3. 一个摘要评估失败后继续处理其他论文。
4. 已标记为 retryable 的 LLM 错误允许在流水线内自动重试，默认最多额外尝试 2 次；退避由可注入策略控制，生产环境使用带抖动的指数退避且单次不超过 30 秒。认证、配置和无效输出等终止性错误不自动重试。
5. 服务重启后，未结束的流水线必须被标记为 interrupted。P0 不自动续跑；用户或下一次调度可创建 `retry_of_job_id` 指向原任务的新流水线。
6. 重试规划器只重新执行没有成功终态事件的抓取单元和没有成功评估记录的论文；成功对象由规范化 arXiv ID、paper_id 和评估并发锁保证不重复处理。
7. 如果外部 LLM 已成功返回、但进程在评估结果入库前中断，系统无法保证外部调用 exactly-once。该论文记录为 `external_outcome_unknown`，重试可能产生一次额外调用和费用，但数据库只保留明确持久化的评估结果。
8. 用户可从任务详情中重新执行失败的抓取单元或缺失摘要评估，但不得重复处理已经成功的对象。

### A8. 细粒度日志与可观测性

#### A8.1 双层日志设计

本轮同时保留两类日志：

1. **结构化事件**：持久化在 SQLite，用于 UI 展示、查询、统计和自动验收。
2. **运行日志**：继续写入 `logs/current.log`，用于开发排障和异常堆栈。

运行日志不得作为判断流水线状态的唯一来源。流水线状态、计数和错误码必须来自数据库中的结构化记录。

#### A8.2 结构化事件最小字段

增加 append-only 的 `job_events` 表，并以现有 `jobs.id` 作为流水线关联 ID。迁移后的最小 schema 为：

| 字段 | 说明 |
|---|---|
| `id INTEGER PRIMARY KEY` | 事件 ID |
| `event_key TEXT NOT NULL UNIQUE` | 幂等事件键；终态事件必须可稳定重建同一 key |
| `job_id INTEGER NOT NULL REFERENCES jobs(id)` | 所属流水线任务 ID |
| `stage TEXT NOT NULL` | `plan`、`crawl_http`、`crawl_parse`、`persist`、`abstract_plan`、`abstract_eval`、`classification`、`direction_backfill`、`investment_memo`、`finalize` |
| `event_type TEXT NOT NULL` | 稳定的事件类型 |
| `level TEXT NOT NULL` | `info`、`warning`、`error` |
| `category TEXT` | 可选，抓取类目 |
| `crawl_date TEXT` | 可选，目标日期 |
| `paper_id INTEGER REFERENCES papers(id)` | 可选，本地论文 ID |
| `arxiv_id TEXT` | 可选，便于人工定位 |
| `attempt INTEGER NOT NULL DEFAULT 1` | 当前尝试次数 |
| `metrics_json TEXT NOT NULL DEFAULT '{}'` | 本事件的结构化计数和耗时 |
| `error_code TEXT` | 稳定、可统计的错误码 |
| `message TEXT NOT NULL DEFAULT ''` | 面向用户的安全摘要 |
| `created_at TEXT NOT NULL` | 带时区的 ISO 8601 UTC 事件时间 |

`evaluations` 增加可空的 `pipeline_job_id INTEGER REFERENCES jobs(id)`，用于从一篇论文回溯到本次抓取和摘要评估。历史评估保持为 NULL。

事件 key 的最低约定：

- 抓取单元终态：`crawl:{job_id}:{crawl_date}:{category}:terminal`
- 摘要论文终态：`abstract:{job_id}:{paper_id}:terminal`
- 单次尝试事件在 key 中追加 `attempt` 和事件类型

每个抓取单元和每篇摘要候选必须产生且只能产生一个终态事件。流水线汇总以终态事件和 `evaluations` 数据为准，不通过解析文本日志计算。

#### A8.3 事件类型

至少支持以下事件：

- `pipeline.started`
- `pipeline.plan_created`
- `crawl.category_started`
- `crawl.http_retrying`
- `crawl.http_succeeded`
- `crawl.http_failed`
- `crawl.parse_completed`
- `crawl.parse_anomaly`
- `crawl.persist_completed`
- `crawl.category_completed`
- `abstract.plan_created`
- `abstract.paper_started`
- `abstract.paper_succeeded`
- `abstract.paper_failed`
- `abstract.paper_skipped`
- `abstract.stage_completed`
- 模块 D 上线后的 `classification.*` 和 `direction_backfill.*` 事件，详细清单见 D10；
- `pipeline.completed`
- `pipeline.interrupted`

#### A8.4 每个抓取单元必须记录的指标

- 目标日期、页面日期、类目、请求 URL。
- HTTP 状态码、重试次数、响应耗时、最终 URL。
- 响应体字节数和内容指纹；默认不把完整 HTML 写入普通日志。
- 页面声明总数、配置 top_n、预期数、解析数。
- 缺少 arXiv ID、标题、Abstract、作者、发布时间的条目数。
- 新增论文数、更新论文数、重复论文数、入库失败数。
- 抓取单元总耗时、最终状态和错误码。

#### A8.5 摘要评估阶段必须记录的指标

- 候选论文数。
- 去重后论文数。
- 因已有成功评估而跳过的数量。
- 因正在运行而跳过的数量。
- 因输入不完整而跳过的数量。
- 成功、失败、重试和终止性失败数量。
- 使用的 Prompt、LLM Profile 和模型标识。
- 阶段总耗时；若 Provider 返回 usage，记录 token 和成本所需的原始计数，但不得因 Provider 不提供 usage 而让任务失败。

#### A8.6 错误码

错误码必须稳定、可测试，至少覆盖：

- `network_timeout`
- `network_http_error`
- `unexpected_redirect`
- `page_date_mismatch`
- `declared_total_unknown`
- `parse_zero_with_nonzero_total`
- `parse_zero_without_total`
- `parse_incomplete`
- `missing_arxiv_id`
- `database_write_failed`
- `evaluation_config_missing`
- `evaluation_already_running`
- `provider_retryable_error`
- `provider_terminal_error`
- `invalid_llm_result`
- `pipeline_interrupted`
- `external_outcome_unknown`

#### A8.7 安全与保留

- 不得记录 API key、Authorization header、Cookie、完整自定义 headers 或会泄露密钥的 URL 参数。
- LLM 原始输出继续由评估记录按现有安全策略保存，不复制进普通 job event。
- 默认持久化结构化事件 30 天；保留期应可配置并纳入现有清理任务。
- 仅在解析异常时允许保存受限大小的诊断 HTML 快照；该能力默认关闭，启用时必须配置保留期，并确保文件名和日志不包含敏感参数。

### A9. UI 需求

#### A9.1 首页任务中心

每个流水线任务应显示：

- 触发来源和目标日期范围。
- 当前阶段：计划、抓取、完整性检查、摘要评估或完成。
- 类目进度：成功、warning、失败和合法空结果数量。
- 论文进度：解析、入库、待评估、成功、失败和跳过数量。
- 最终状态及耗时。

模块 D 上线后还应显示分类阶段状态，以及 matched、possible、unmatched、failed 和无方向合法跳过数量。

#### A9.2 任务详情

用户应能展开一次流水线，按“日期 → 类目 → 阶段”查看结构化事件。默认优先显示 warning 和 error，并可查看完整事件时间线。

任务详情至少支持：

- 只看失败或 warning。
- 按类目筛选。
- 定位失败论文。
- 复制安全的诊断摘要。
- 重新执行失败单元或缺失摘要评估。

#### A9.3 文案调整

- “抓取最新 Metadata”改为“抓取并摘要评估”。
- 正常完成显示“今日情报已更新”。
- 部分成功显示“已完成，但存在 N 个类目或 M 篇论文失败”。
- 不得把 warning 或 partial_success 显示成完全成功。

### A10. 数据与兼容性要求

1. 现有 `papers`、`paper_categories`、`evaluations` 和历史任务数据必须继续可用。
2. 新表和新字段通过向前兼容的 SQLite migration 创建。
3. 现有手工摘要评估入口继续可用。
4. 原始 `crawl` 和 `abstract_eval` 任务类型可作为内部或兼容路径保留，但正常 UI 与 scheduler 应使用完整流水线。
5. 现有 CSV、论文详情和 Prompt/LLM 配置行为不因本模块改造改变；当前“收藏”页的语义调整由模块 B 单独迁移。

### A11. 验收标准

#### A11.1 功能验收

1. 用户点击一次“抓取并摘要评估”，系统自动完成两个阶段。
2. 定时器运行后，无需人工操作即可产生摘要评估结果。
3. 同一论文出现在多个类目时只自动评估一次。
4. 已成功评估的论文不会因 Rank 或 Stars 更新而重复评估。
5. 一个类目失败时，成功类目仍能入库并完成摘要评估，最终状态为 partial_success。
6. 页面声明有论文但解析为 0 时，抓取单元必须失败并记录明确错误码。
7. 合法空类目被记录为 empty_success，而不是失败。
8. 重复提交兼容流水线不会产生两个并行任务或重复评估。
9. 服务中断后任务被标记为 interrupted，不会自动续跑；基于 `retry_of_job_id` 重新执行时不会重复成功结果。
10. 任一 warning 均使最终状态成为 partial_success；全类目合法空结果仍为 success。

#### A11.2 日志验收

1. 任意一次流水线都可以按 job ID 查出完整阶段时间线。
2. 任意失败都能定位到日期、类目、阶段；论文级失败还应定位到 arXiv ID。
3. 抓取详情能看到预期数、解析数、新增数、更新数、重复数和失败数。
4. 摘要评估详情能看到候选、跳过、成功、失败和重试数量。
5. 结构化事件中的汇总数量与数据库最终结果一致。
6. 日志中不出现 API key、Authorization header 或完整敏感配置。

#### A11.3 自动化测试验收

必须增加以下测试：

- 定时流水线自动串联抓取和摘要评估。
- 手工最新抓取和补抓流程自动串联摘要评估。
- 多类目部分失败仍继续评估成功数据。
- 页面声明总数与解析数一致、合法空、未知总数和异常空结果。
- 同一论文跨类目候选去重。
- 已成功评估和正在评估论文的跳过逻辑。
- retryable 与 terminal LLM 错误的不同处理。
- 流水线重复触发幂等性。
- 服务中断后的状态恢复。
- job event 计数与最终数据库结果一致。
- 结构化日志和文本日志的敏感信息脱敏。

完整测试集必须全绿，且测试不得访问真实 papers.cool、真实 LLM、仓库内生产数据库、密钥、缓存或日志。

### A12. 产品指标

上线后至少观测：

- 启用类目抓取完成率。
- `抓取日期 × 类目` 数据完整率。
- 抓取后摘要评估自动触发率。
- 摘要评估成功率和终止性失败率。
- 每日流水线完全成功率与部分成功率。
- 从流水线启动到可浏览摘要评估结果的 P50/P95 时长。
- 每日重复评估拦截数量。
- 需要人工介入修复的运行次数。

首个稳定版本的目标：

- 抓取后摘要评估自动触发率不低于 99%。
- 每个成功抓取单元均有可核对的完整性计数。
- 单篇失败不阻塞批量任务。
- 不因跨类目重复或重复触发创建重复摘要评估。

### A13. 建议实施拆分

#### Slice A1：流水线状态与结构化事件

- 增加完整流水线任务类型和状态。
- 增加 job events 存储与查询。
- 建立统一的 run/job 关联 ID。

#### Slice A2：抓取完整性与细粒度日志

- 解析页面总数和页面日期。
- 记录 HTTP、解析和入库指标。
- 增加异常空结果、warning 和错误码。

#### Slice A3：自动摘要评估

- 生成并去重候选。
- 自动执行摘要评估。
- 处理重复、重试、部分成功和中断。

#### Slice A4：任务中心与验收

- 展示阶段、类目和论文计数。
- 增加任务详情和失败筛选。
- 补齐集成测试和日志脱敏测试。

### A14. 风险与处理

#### papers.cool 当日确实没有论文

不能把所有 0 结果都当成解析失败。必须优先使用页面声明总数区分合法空结果和解析异常；无法确认时使用 warning，而不是假装完全成功。

#### 摘要评估增加每日运行时间和费用

自动评估只处理缺失成功评估的论文，并严格去重；沿用现有摘要并发设置，保留手工暂停 scheduler 的能力。

#### 结构化事件数量增长

事件按保留期清理。论文级成功事件可在高负载下进行汇总，但失败和跳过事件必须保留到论文级。

#### 日志变详细后泄露配置

所有事件 payload 使用白名单字段；禁止直接序列化 HTTP 请求对象、Profile 或完整异常上下文。

### A15. 待确认项

以下问题不阻塞 v0.1 评审，但在进入实现前应确认：

1. 结构化事件默认保留 30 天是否合适。
2. 是否需要保留一个仅抓 Metadata、不自动评估的管理员入口；本 PRD 默认正常 UI 不提供。
3. 解析异常时是否允许手工开启诊断 HTML 快照；本 PRD 默认关闭。
4. 标题或 Abstract 变化后是否应自动重新摘要评估；本 PRD 默认不自动重评。

### A16. 文档关系

本模块是现有 `PRD.md` 的 P0 改造补充。若两者冲突，本模块仅在以下范围内优先：

- 每日抓取与补抓任务的编排方式。
- 抓取后的自动摘要评估。
- 抓取完整性判定。
- 抓取和摘要评估的结构化日志、状态与验收标准。

其他功能仍以主 PRD 和当前已确认产品决策为准。

## 模块 B：全文评估后的个人整理（P1）

### B1. 可行性结论

该需求**较容易实现，整体为低到中等复杂度**。现有论文详情页已经能判断并展示最近一次成功的全文评估，SQLite 也已有论文、评估和向前迁移机制。新增能力主要是本地状态、主题 CRUD、三张表和少量 Flask 路由，不依赖新的爬虫、LLM 或外部服务。

真正需要谨慎处理的不是按钮本身，而是以下产品语义：

1. 当前导航中的“收藏”实际展示全部成功完成全文评估的论文，并不是真正收藏。
2. 收藏与跳过应互斥，但加入投资主题是独立归档关系，不应与前两者互斥。
3. 主题需要支持长期维护，不能因改名或归档而丢失论文关系。
4. 所有写操作必须确认论文确实存在成功的全文评估，不能只靠前端隐藏按钮。

### B2. 用户流程

```text
打开论文详情
  → 阅读成功的全文评估结果
  → 在结果下方选择“收藏”或“跳过”
  → 可选：从已有投资主题中选择一个或多个并保存
  → 若没有合适主题，进入投资主题设置创建后再选择
```

操作区只在存在至少一次 `fulltext_review + success` 记录时显示。后续某次重新全文评估失败，不应抹掉已有成功评估对应的个人整理状态。

### B3. 功能需求

#### B3.1 收藏与跳过

- 默认状态为“未处理”，数据库可用无记录表达该状态。
- “收藏”和“跳过”属于同一个个人决策维度，同一论文不能同时处于两种状态。
- 用户从“收藏”切换为“跳过”时直接更新状态，反向同理。
- 用户可以“恢复未处理”，但该操作不删除主题归档和团队跟踪。
- “跳过”只表示不再优先阅读，不删除论文、评估、缓存和历史数据。
- 重复提交当前状态返回成功，不新增重复记录。

#### B3.2 加入投资主题

- 投资主题类似收藏夹，由用户手动创建和维护。
- 一篇论文可加入多个投资主题；一次保存可勾选一个或多个主题。
- 加入主题与收藏/跳过相互独立：收藏或跳过的论文都可以保留主题关系。
- 用户可以从论文详情页增加或移除主题关系。
- 若当前没有可用主题，操作区显示“创建投资主题”入口，不提供模型自动创建。
- 已归档主题不能被新加入；已有归档主题关系继续显示，只有用户执行明确的“从论文移除”操作时才删除。保存活跃主题多选不得隐式删除归档主题关系。

#### B3.3 投资主题设置

主题设置页至少支持：

- 新建主题：名称必填，说明可选。
- 重命名主题：保留原有论文关系。
- 编辑说明。
- 归档与恢复：归档后默认不出现在论文选择器中，但历史关系和主题详情仍保留。
- 查看主题内论文：至少支持按加入时间、全文评分和论文标题排序。

首版不提供硬删除。主题名称使用 `NFKC → 去除首尾空白 → 将连续空白压缩为单个空格 → casefold` 生成 `normalized_name`；规范化后必须唯一，且归档主题继续占用该唯一名称。主题名称限制为 1～80 个字符，说明限制为 500 个字符；超限请求返回字段错误且不写入。

#### B3.4 “收藏”页面语义迁移

当前 `/favorites` 页面展示的是全部成功完成全文评估的论文。上线本模块时必须完成以下迁移：

1. 将当前列表改名为“全文库”或“已全文评估”，建议使用 `/reviewed-papers`。
2. `/favorites` 改为只展示个人决策为 `favorite` 的论文。
3. 现有已全文评估论文默认保持“未处理”，不得批量自动标记为收藏。
4. 导航同时提供“全文库”“收藏”“投资主题”；若需要控制导航数量，可把“全文库”放入论文列表筛选。

#### B3.5 页面与操作反馈

全文评估结果下方增加“后续操作”区：

- 收藏按钮：显示当前激活状态，激活时提供取消入口。
- 跳过按钮：显示当前激活状态，激活时提供恢复未处理入口。
- 加入主题：使用复选列表或多选控件，保存后在页面展示主题标签。
- 所有操作完成后回到当前论文的 `#fulltext-result` 位置，并显示明确的成功或错误提示。
- 主题被其他页面归档后，论文详情仍显示历史主题标签，并标注“已归档”。

### B4. 数据模型

#### `paper_dispositions`

| 字段 | 说明 |
|---|---|
| `paper_id INTEGER PRIMARY KEY REFERENCES papers(id) ON DELETE CASCADE` | 一篇论文只有一个个人决策 |
| `decision TEXT NOT NULL` | `favorite` 或 `skipped`；无记录表示未处理 |
| `created_at TEXT NOT NULL` | 当前连续决策记录的创建时间；清除后再选择会重新生成 |
| `updated_at TEXT NOT NULL` | 最近修改时间 |

#### `investment_themes`

| 字段 | 说明 |
|---|---|
| `id INTEGER PRIMARY KEY` | 主题 ID |
| `name TEXT NOT NULL` | 展示名称 |
| `normalized_name TEXT NOT NULL UNIQUE` | 去空格、大小写不敏感后的去重键 |
| `description TEXT NOT NULL DEFAULT ''` | 主题说明 |
| `status TEXT NOT NULL DEFAULT 'active'` | `active` 或 `archived` |
| `created_at / updated_at TEXT NOT NULL` | 审计时间 |

#### `paper_investment_themes`

| 字段 | 说明 |
|---|---|
| `paper_id INTEGER NOT NULL REFERENCES papers(id) ON DELETE CASCADE` | 论文 |
| `theme_id INTEGER NOT NULL REFERENCES investment_themes(id) ON DELETE RESTRICT` | 投资主题 |
| `created_at TEXT NOT NULL` | 加入时间 |

联合唯一键为 `(paper_id, theme_id)`。删除论文时级联删除关系；主题首版只归档，数据库拒绝删除仍有关联关系的主题。

建议至少建立 `paper_dispositions(decision, updated_at)`、`paper_investment_themes(theme_id, created_at)` 和 `paper_investment_themes(paper_id)` 索引，列表查询必须批量加载，避免逐论文查询。

### B5. 路由与服务边界

建议沿用现有 Flask route/service/database 分层。首版 HTML 操作统一使用 `application/x-www-form-urlencoded`，成功后执行同源 302/303 redirect 并使用 flash 提示；字段非法返回 400 且零写入，论文或实体不存在返回 404，无成功全文资格返回 409。

表单与路由契约如下：

- `POST /api/papers/<paper_id>/decision`：字段 `decision=favorite|skipped|clear`。`clear` 删除当前决策行；首版不保留决策变更历史。
- `POST /api/papers/<paper_id>/investment-themes`：使用重复字段 `theme_ids=<int>` 提交活跃主题集合。空集合表示移除全部**活跃主题**关系；接口保留所有归档主题关系。
- `POST /api/papers/<paper_id>/investment-themes/<theme_id>/remove`：显式移除一个主题关系，包括已归档主题。
- `GET /favorites`：真正收藏列表。
- `GET /reviewed-papers`：全部成功全文评估列表，并支持 `decision=all|undecided|favorite|skipped` 筛选。
- `GET /investment-themes`：主题设置和主题列表。
- `POST /investment-themes`：字段 `name`、`description`，创建主题。
- `POST /investment-themes/<theme_id>`：字段 `action=update|archive|restore`；`update` 同时接受 `name`、`description`。
- `GET /investment-themes/<theme_id>/papers`：查看主题内论文。

数据库写入函数必须在事务中完成资格校验与状态更新。前端隐藏操作区只是交互规则，不是权限或数据完整性保证。

### B6. 验收标准

1. 未成功完成全文评估的论文详情不显示后续操作，直接请求写接口也被拒绝。
2. 成功完成全文评估的论文可以收藏、跳过、恢复未处理，收藏与跳过不会同时存在。
3. 一篇论文可以加入多个主题，重复保存不会产生重复关系。
4. 主题可创建、重命名、归档和恢复；这些操作不丢失论文关系。
5. `/favorites` 只展示真正收藏的论文；全部已全文评估论文仍有独立入口。
6. 现有论文、评估和缓存数据迁移后保持可用，历史论文不会自动变成收藏。
7. 路由测试覆盖 CSRF、非法决策、无全文资格、未知主题、归档主题和重复提交。
8. 数据库测试覆盖唯一键、状态切换、主题多对多关系和事务回滚。

### B7. 首版明确延期

- 论文备注、优先级、提醒日期和阅读进度。
- 主题层级、主题合并和批量移动。
- 根据 LLM 结果自动加入主题。
- 根据收藏/跳过行为训练个性化推荐或自动改写评分。
- 多设备同步和协作分享。

### B8. 业务指标

- 成功全文评估论文的个人决策覆盖率。
- 收藏、跳过和未处理论文数量。
- 被加入至少一个投资主题的全文论文占比。
- 活跃投资主题数量及每个主题的新增论文趋势。

这些指标只用于观察工作流是否有效，不作为模型自动判断投资价值的训练标签，除非后续另行确认。

## 模块 C：手动团队跟踪与实体库（P1）

### C1. 可行性结论

该需求**可以实现，首版为中等复杂度**。难点主要在人物和机构的重复、同名、改名及任职变化，而不是表单和数据库本身。采用“第一作者 + 一个主要机构/企业 + 用户手工确认”的边界后，可以完全避免首版处理 PDF 机构识别、多作者校验、外部数据源和复杂实体消歧，因此适合作为独立 P1 模块。

现有 `papers.authors` 已保存作者数组，可以把第一项作为表单预填值；该顺序只是抓取结果，不能被视为可信的第一作者证明，用户仍需检查或修改。机构/企业信息不从当前首页或 PDF 自动推断。人工确认结果必须写入独立实体表，不能回写 `papers.authors`，因为后续抓取会更新该原始元数据快照。

### C2. 用户流程

```text
阅读成功的全文评估
  → 点击独立的“跟踪团队”操作
  → 系统预填第一作者姓名
  → 用户确认或修改作者
  → 选择已有机构/企业，或手工新建并分类
  → 保存论文、第一作者和机构/企业的跟踪关系
  → 后续在研究对象页面按作者或机构查看相关论文
```

“跟踪团队”与收藏、跳过、加入投资主题完全独立。用户可以跳过一篇论文，但仍跟踪其团队；也可以收藏论文但不跟踪团队。

### C3. 功能需求

#### C3.1 跟踪入口与资格

- 入口位于全文评估结果下方，作为独立的“是否跟踪团队”操作区。
- 只对存在成功全文评估的论文开放，后端写接口必须重复校验。
- 未跟踪时显示“跟踪团队”；已跟踪时显示作者、机构、跟踪状态和“编辑/停止跟踪”。
- “停止跟踪”将关系标记为归档，不删除作者库、机构库或论文历史。

#### C3.2 手工录入

- 第一作者姓名默认取 `authors_list[0]`，用户可修改；若没有作者数据则显示空输入框。
- 用户优先从已有作者库选择，也可以新建作者。
- 用户优先从已有机构/企业库选择，也可以新建机构/企业。
- 首版每篇论文只记录一个主要第一作者和一个主要机构/企业。
- 作者名称和机构/企业名称必填；机构类型必填。
- 可选填写作者分类、地区和备注，但不得把填写这些字段作为完成跟踪的前提。

#### C3.3 作者库

作者记录至少支持：

- 姓名。
- 分类：`academic`（学术）、`industry`（产业）、`hybrid`（跨界）或 `unknown`。
- 备注。
- 状态：活跃或归档。
- 关联论文数量和关联机构数量的派生展示。

首版不建立强制的“当前任职机构”字段。作者可能随时间变更机构，具体关系应保留在论文跟踪记录中，避免后一次编辑覆盖历史。

#### C3.4 机构/企业库

机构记录至少支持：

- 名称。
- 类型：`university`（高校）、`research_institute`（研究机构）、`company`（企业）或 `other`。
- 国家/地区，可选。
- 备注。
- 状态：活跃或归档。
- 关联作者和论文数量的派生展示。

#### C3.5 实体去重

- 新建作者或机构时，使用 `NFKC → 去除首尾空白 → 将连续空白压缩为单个空格 → casefold` 后的名称做精确去重。
- 命中精确重复时提示并要求复用已有记录，不创建第二条。
- 首版不做模糊自动合并。例如 `MIT` 与 `Massachusetts Institute of Technology` 可暂时共存，避免错误合并。
- 实体合并、别名管理和外部唯一 ID 在后续版本处理；在此之前允许用户编辑名称和归档误建记录。
- 已归档作者或机构不能用于新的跟踪记录；已有论文关系继续可见。归档实体本身不自动归档其论文跟踪关系，用户需在关系层明确停止跟踪。
- 归档实体继续占用规范化唯一名称；再次录入同名对象时提示恢复或复用，不能绕过归档状态创建重复实体。

精确重名冲突使用以下确定流程：

1. `mode=new` 命中已有实体时，服务器返回 409 且整次团队保存零写入。
2. 错误页面或原表单展示冲突实体的 `id`、名称和状态。
3. 活跃实体提供“使用该记录”操作，前端改为 `mode=existing` 并提交对应 ID。
4. 归档实体先提供“恢复该记录”操作；恢复成功后再以 `mode=existing` 重新提交团队关系。
5. 服务器不得在重名时静默复用或隐式恢复，避免同名不同人的错误关联。

#### C3.6 研究对象页面

增加统一“研究对象”页面，至少包含三个视图：

1. 跟踪中的论文：论文、第一作者、机构/企业、开始跟踪时间和备注。
2. 作者库：作者分类、关联机构、关联论文数量和最近论文。
3. 机构/企业库：机构类型、地区、关联作者、关联论文数量和最近论文。

首版支持按名称、作者分类、机构类型和状态筛选；不要求关系图谱或时间线可视化。

### C4. 数据模型

#### `research_authors`

| 字段 | 说明 |
|---|---|
| `id INTEGER PRIMARY KEY` | 作者实体 ID |
| `name TEXT NOT NULL` | 展示姓名 |
| `normalized_name TEXT NOT NULL UNIQUE` | 精确去重键 |
| `author_category TEXT NOT NULL DEFAULT 'unknown'` | `academic/industry/hybrid/unknown` |
| `notes TEXT NOT NULL DEFAULT ''` | 人工备注 |
| `status TEXT NOT NULL DEFAULT 'active'` | `active/archived` |
| `created_at / updated_at TEXT NOT NULL` | 审计时间 |

#### `research_organizations`

| 字段 | 说明 |
|---|---|
| `id INTEGER PRIMARY KEY` | 机构实体 ID |
| `name TEXT NOT NULL` | 展示名称 |
| `normalized_name TEXT NOT NULL UNIQUE` | 精确去重键 |
| `organization_type TEXT NOT NULL` | `university/research_institute/company/other` |
| `region TEXT NOT NULL DEFAULT ''` | 国家或地区 |
| `notes TEXT NOT NULL DEFAULT ''` | 人工备注 |
| `status TEXT NOT NULL DEFAULT 'active'` | `active/archived` |
| `created_at / updated_at TEXT NOT NULL` | 审计时间 |

#### `paper_team_tracking`

| 字段 | 说明 |
|---|---|
| `id INTEGER PRIMARY KEY` | 跟踪记录 ID |
| `paper_id INTEGER NOT NULL UNIQUE REFERENCES papers(id) ON DELETE CASCADE` | 首版一篇论文一条团队记录 |
| `lead_author_id INTEGER NOT NULL REFERENCES research_authors(id) ON DELETE RESTRICT` | 手工确认的第一作者 |
| `organization_id INTEGER NOT NULL REFERENCES research_organizations(id) ON DELETE RESTRICT` | 手工确认的主要机构/企业 |
| `status TEXT NOT NULL DEFAULT 'tracking'` | `tracking/archived` |
| `notes TEXT NOT NULL DEFAULT ''` | 这篇论文维度的判断与备注 |
| `created_at / updated_at TEXT NOT NULL` | 审计时间 |

作者与机构的关系从论文跟踪记录中派生。未来确实需要记录任职时间、职位或脱离论文的关系时，再增加独立 `author_organization_links`，首版不预建空泛图谱结构。

建议至少建立 `paper_team_tracking(status, updated_at)`、`paper_team_tracking(lead_author_id)` 和 `paper_team_tracking(organization_id)` 索引，作者库和机构库的关联计数使用批量聚合查询。

### C5. 路由与服务边界

团队模块沿用 `application/x-www-form-urlencoded`、POST、CSRF、同源 redirect 和 flash。字段非法返回 400 且零写入，论文或实体不存在返回 404，无成功全文资格返回 409，提交已归档作者或机构返回 409 并提示先恢复实体。

- `POST /api/papers/<paper_id>/team-tracking`：新建、更新或重新激活论文团队跟踪。字段：
  - `author_mode=existing|new`；existing 时提交 `author_id`，new 时提交 `author_name`、可选 `author_category` 和 `author_notes`。
  - `organization_mode=existing|new`；existing 时提交 `organization_id`，new 时提交 `organization_name`、必填 `organization_type`、可选 `organization_region` 和 `organization_notes`。
  - 可选 `tracking_notes`。
- `POST /api/papers/<paper_id>/team-tracking/archive`：只需 CSRF 字段，停止跟踪并归档关系；重复归档幂等。
- `GET /research-entities`：研究对象总览，查询字段 `view=tracking|authors|organizations`，并支持名称、类型和状态筛选。
- `POST /research-authors/<author_id>`：字段 `action=update|archive|restore`；update 接受 `name`、`author_category`、`notes`。
- `POST /research-organizations/<organization_id>`：字段 `action=update|archive|restore`；update 接受 `name`、`organization_type`、`region`、`notes`。

一次创建团队跟踪时，如果同时新建作者和机构，三者必须在一个事务中提交；任一字段或唯一性检查失败时零写入。

已归档的论文跟踪关系可通过同一保存流程重新激活；重新激活更新原记录，不创建第二条关系，保留原 `created_at` 并更新 `updated_at`。如果其作者或机构已归档，必须先恢复实体，不能在保存关系时隐式恢复。

### C6. 验收标准

1. 只有成功全文评估的论文能创建团队跟踪记录。
2. 第一作者由论文元数据预填，但必须允许用户确认或修改。
3. 用户可复用已有作者、机构，也可在同一流程中新建并分类。
4. 同一规范化名称不能重复创建；系统不做未经确认的模糊合并。
5. 一篇论文首版只能有一条团队跟踪记录，可编辑或归档，不产生重复关系。
6. 作者库和机构库分别可查询、筛选、编辑和归档，并能查看关联论文。
7. 作者变更机构时，旧论文关系不会被全局“当前机构”覆盖。
8. 同时新建作者、机构和跟踪关系时具备事务原子性。
9. 路由与数据库测试覆盖无全文资格、缺失字段、重复实体、归档实体、重复提交和事务回滚。

### C7. 首版明确延期

- 从 PDF、arXiv 首页或网页自动识别机构。
- 同时记录多名作者、多家机构和作者排序校验。
- 作者/机构别名、模糊匹配、自动合并和外部唯一 ID。
- 自动补充任职经历、融资、专利、GitHub 或公司工商信息。
- 团队提醒、人员流动监控和外部通知。
- 主题与团队之间的自动关联或多主题校验。

### C8. 业务指标

- 被标记跟踪团队的全文论文数量与占比。
- 活跃作者、活跃机构/企业数量。
- 作者和机构记录的复用率。
- 因精确重名被拦截的重复创建次数。
- 跟踪记录中作者、机构分类和地区字段的完整度。

## 模块 D：用户定义关注方向的自动筛选与增量分类（P2）

### D1. 产品结论与可行性

该需求为**中等复杂度**，不需要增加新的论文来源，但会在每日流水线中新增一个独立、轻量的 LLM 分类阶段。它取代原“由系统自动发现趋势”的首版设想，采用以下产品原则：

> 关注方向必须由用户定义；LLM 只负责依据论文 Metadata 执行分类，不得自行创建方向。自动摘要评估只处理匹配或可能匹配的论文，分类选择权和最终人工判断权保留给用户。

该模块的主要价值是减少每日摘要评估量和阅读量，而不是生成趋势结论。自动发现未知技术趋势延期到后续模块。

### D2. 关注方向与投资主题的边界

| 维度 | 关注方向 | 投资主题 |
|---|---|---|
| 目的 | 阅读前的自动筛选规则 | 阅读后的个人研究归档 |
| 阶段 | 抓取入库后、摘要评估前 | 成功全文评估后 |
| 创建者 | 用户 | 用户 |
| 论文关系 | LLM 分类结果，可由用户确认或否决 | 只能由用户手工加入 |
| 自动化影响 | 决定论文是否自动摘要评估 | 不影响抓取和评估流程 |
| 判断依据 | 标题、Abstract、Subjects 和抓取类目 | 全文评估和用户投资判断 |

两者必须使用独立的数据表、设置页面和论文关系。LLM 的关注方向匹配不得自动创建投资主题，也不得自动把论文加入投资主题。

### D3. 关注方向设置

#### D3.1 用户字段

用户只填写两个字段：

- **方向名称**：必填，用于展示和选择；规范化后在未归档方向中唯一。
- **范围简介**：必填的自然语言文本，由用户自行描述纳入范围、边界、正例、反例或需要排除的内容。

范围简介作为不透明文本完整传给分类 Prompt。首版不拆分关键词、负面关键词、权重、行业、技术层级或其他结构化字段，也不做语义硬校验。

#### D3.2 生命周期

- 首版只支持新增和归档，不支持修改、临时停用或重新启用。
- 保存后的方向名称和范围简介不可修改。
- 需要调整定义或暂时停止使用时，用户新建替代方向或归档旧方向。
- `active` 方向参与每日分类；`archived` 方向默认隐藏，只用于回溯历史结果，归档是终态。
- 已产生分类结果的方向不得硬删除。
- 归档方向可释放规范化名称；历史记录始终通过不可变 `direction_id` 关联并展示当时保存的名称和范围。

由于方向内容不可修改，首版不引入方向版本、历史分类失效或自动重算机制。

### D4. 每日轻量分类流程

#### D4.1 输入与调用方式

分类输入只使用已保存的论文 Metadata：

- 标题；
- Abstract；
- Subjects；
- 本次抓取类目。

不得使用之前生成的中文摘要或全文评估作为自动分类输入。缺少标题或 Abstract 的论文不调用分类模型，记录为输入不完整，也不自动进入摘要评估。

每篇新论文创建一个逻辑分类任务，一次性传入本次流水线计划快照中的全部 `active` 关注方向。一个逻辑分类任务可因 retryable 错误产生初次请求加最多 2 次重试，但不会按方向拆成多次独立调用。允许一篇论文同时匹配多个方向。分类使用独立的 `direction_classification` Prompt 和默认 LLM Profile，不与完整摘要评估 Prompt/Profile 绑定；用户可选择更便宜、更快的模型。

首版分类并发复用现有 `llm.abstract_concurrency`，不增加第二个并发设置；Provider 超时、错误分类和退避复用现有 LLM 策略。分类与摘要评估分别统计调用量和 token usage。

分类任务创建时必须固化方向 ID、名称、范围简介、Prompt、Profile 和模型快照。运行过程中新增或归档方向不改变本次计划。

#### D4.2 无启用方向

当计划快照中没有任何 `active` 关注方向时：

1. 分类阶段状态为 `skipped_no_active_directions`，不调用分类 LLM。
2. 继续按模块 A 的原有规则自动摘要评估全部合格新论文。
3. 首页和任务详情显示：“当前未启用关注方向，将对全部新论文执行摘要评估。”
4. 如果用户希望完全暂停自动摘要评估，应使用独立的 scheduler/自动评估开关，不使用“零关注方向”表达暂停。

#### D4.3 有启用方向

```text
抓取并保存全部论文 Metadata
  → 生成本次启用关注方向快照
  → 每篇新论文调用一次轻量分类
      → matched：建立自动分类关系，进入摘要评估
      → possible：保存待确认候选，进入摘要评估
      → unmatched：停止自动处理，保留手动摘要评估入口
      → failed：按策略重试；最终失败后停止自动处理并进入失败列表
  → 对 matched / possible 论文去重
  → 只对缺少成功摘要评估的论文执行摘要评估
```

同一论文跨多个抓取类目或同时匹配多个方向时，分类调用和摘要评估均只执行一次。论文仅因在后续日期重复出现，不自动重新分类；新建方向对历史论文的处理必须通过 D7 的手动历史补分类触发。

论文 Metadata、分类 Prompt 或分类 Profile 后续发生变化时，首版也不自动重算已有成功分类；用户只能对尚无成功结果或失败结果使用本模块定义的明确入口。

### D5. 分类结果与有效分类

#### D5.1 模型状态

- `matched`：论文的主要问题、核心方法或主要应用直接属于该方向。自动形成有效关注方向分类，并进入摘要评估。
- `possible`：属于相关基础技术、邻近应用，或仅凭 Abstract 无法确定。进入摘要评估，但不形成有效关注方向分类，等待用户处理。
- `unmatched`：核心贡献不属于该方向。没有任何方向为 `matched/possible` 时，不自动摘要评估。
- `failed`：模型调用、结果解析或契约校验失败。不得转换为 `unmatched`。

分类模型必须对计划中的每个方向返回 `direction_id`、状态和简短原因，不得返回计划外方向或自由生成新名称。稳定输出契约为：

```json
{
  "directions": [
    {
      "direction_id": 12,
      "decision": "matched",
      "reason": "论文的核心贡献是端侧多模态模型的低比特推理。"
    },
    {
      "direction_id": 19,
      "decision": "unmatched",
      "reason": "论文不涉及该方向的核心问题或应用。"
    }
  ]
}
```

缺少计划方向、重复方向、未知 ID、未知状态或非对象 JSON 均视为无效结果并进入可统计错误。

一次调用的多方向输出采用原子校验：只有计划中每个方向都恰好返回一条合法结果时，该次尝试才成功，并在一个事务中写入全部方向结果。部分合法、部分缺失或非法的输出整体作废，不保存部分成功方向。整体 Provider/契约失败在自动重试耗尽后，为本次方向快照中的每个方向写入 `failed` 结果，并关联同一个终态 classification evaluation。`paper_direction_results` 不用 NULL 表示已尝试失败。

#### D5.2 论文级聚合状态

一篇论文面对多个方向时，论文级主状态按 `matched > possible > failed > unmatched` 聚合：

1. 任一方向为 `matched`，论文主状态为 `matched`。
2. 没有 matched、但任一方向为 `possible`，主状态为 `possible`。
3. 没有 matched/possible、但任一方向最终失败，主状态为 `failed`。
4. 全部方向均明确为 `unmatched`，主状态才是 `unmatched`。

任一方向为 matched 或 possible 即可进入摘要评估。与此同时，只要其他方向存在最终失败，本次分类仍带 `has_partial_failure=true`，流水线至少为 `partial_success`，不能用论文主状态掩盖方向级失败。由于单次多方向输出原子写入，这种混合状态只会来自同一论文在不同逻辑分类任务中的结果，例如旧方向已 matched、后来对新增方向的历史补分类最终失败。

#### D5.3 人工处理

对 `possible` 论文，用户可以：

- 确认一个或多个模型建议方向；
- 改选其他当前未归档的方向；
- 标记为不相关。

对 `unmatched` 论文，用户可以手工触发现有摘要评估；手工评估属于显式绕过自动门控，不改变模型原始分类。评估后用户仍可手工选择关注方向。

用户可以否决模型的 `matched` 判断。人工确认或否决作为独立字段保存，不覆盖模型原始状态、原因、Prompt、Profile 和时间。

有效分类按以下优先级派生：

1. 人工 `confirmed`：属于该方向。
2. 人工 `rejected`：不属于该方向。
3. 无人工结果且模型为 `matched`：属于该方向。
4. 无人工结果且模型为 `possible/unmatched/failed`：不属于正式分类；`possible` 显示为待确认。

首版不使用人工修正训练模型、生成个性化权重或自动改写关注方向。

人工结果保存后立即重新计算有效分类和默认列表：否决最后一个有效 matched 后，论文若也没有待确认 possible，则退出默认列表；确认 possible 或手工选择其他方向后，论文立即进入或保留在默认列表。模型原始状态和原因始终展示且不可覆盖。

### D6. 论文列表与操作

- 存在启用方向时，默认论文列表只展示按人工覆盖后仍至少有一个有效 `matched` 或待确认 `possible` 的论文。
- 没有启用方向时不存在分类结果，默认列表展示全部符合摘要评估条件的论文，保持模块 A 的原有行为。
- 支持按关注方向、模型状态和人工状态筛选。
- `possible` 显示“待确认分类”和模型建议方向。
- `unmatched`、`failed` 通过独立筛选入口查看，不混入默认每日阅读列表。
- `unmatched` 论文保留“手动摘要评估”入口。
- 论文详情展示模型原始结果、原因、人工判断和最终有效分类，不把关注方向显示为投资主题。
- 人工操作后返回当前论文或原筛选列表，并显示明确反馈。

所有抓取论文 Metadata 均保留在数据库中。`unmatched` 只表示停止自动 LLM 深度处理，不表示删除、隐藏到不可访问或阻止未来历史补分类。

### D7. 新增方向后的历史补分类

#### D7.1 触发规则

- 新建关注方向后不自动处理历史论文。
- 用户可在方向设置页手动选择该方向、开始日期和结束日期，创建一次历史补分类任务。
- 首版只允许对新增方向执行补分类，不重算其他方向，也不覆盖已有成功分类。
- 日期范围按 `paper_categories.crawl_date` 解释：论文只要至少有一条类目记录落在闭区间 `[date_from, date_to]` 就进入去重候选集。
- 候选集按 `paper_id` 去重；分类输入中的类目使用该日期范围内该论文所有不同 `paper_categories.category` 的排序后并集。
- 范围内所有具有有效标题和 Abstract 的去重论文均为可执行候选，不只处理此前 `unmatched` 的论文；一篇论文可以同时属于多个方向。
- 范围内缺少标题或 Abstract 的论文计入 `input_incomplete`，不调用分类模型、不进入摘要评估，但必须出现在预览与任务汇总中。
- 补分类输入仍使用原始 Metadata，不使用已有摘要评估结果。

#### D7.2 执行前预览

用户确认前至少展示：

- 目标方向和日期范围；
- 日期范围内去重论文总数、可执行候选数和 `input_incomplete` 数量；
- 已有该方向成功分类、将被幂等跳过的数量；
- 已有成功摘要评估的数量；
- 最多可能新增的摘要评估数量。

预览数量是成本上限提示，不保证所有候选都会匹配。用户确认后才创建任务。

#### D7.3 分类后的摘要评估

- 新结果为 `matched` 或 `possible`，且已有成功摘要评估：只保存分类结果，不重复评估。
- 新结果为 `matched` 或 `possible`，且没有成功或正在运行的摘要评估：在同一任务中自动继续摘要评估。
- 新结果为 `unmatched`：停止处理，保留手工评估入口。
- 新结果为 `failed`：按错误策略重试，最终失败后进入失败列表，不自动摘要评估。
- 同一补分类任务中的多论文摘要评估继续复用 `llm.abstract_concurrency`。

分类和后续摘要评估共享同一个父任务 ID。任务详情必须能区分分类阶段与摘要评估阶段。

#### D7.4 幂等与重试

- `(paper_id, direction_id)` 是分类结果的逻辑唯一键。
- 重复执行相同方向和重叠时间段时，已有 `matched/possible/unmatched` 成功结果默认跳过。
- 只有 `failed` 或没有结果的论文进入重试；首版不提供强制覆盖成功分类。
- 已有成功摘要评估或兼容评估正在运行时不创建重复评估。
- 部分论文失败不阻止其他论文继续分类和评估。
- 分类和摘要评估分别执行最多 2 次额外自动重试，并分别保存错误与终态；分类成功不代表摘要评估成功，反之亦然。
- 自动重试只发生在创建它的每日或历史补分类任务内。重试耗尽后的分类 `failed` 和终止性摘要评估失败不会因下一次日常任务无限重跑，只能通过明确的失败重试或单篇手动评估入口重新执行。

### D8. 数据模型

#### `attention_directions`

| 字段 | 说明 |
|---|---|
| `id INTEGER PRIMARY KEY` | 不可变方向 ID |
| `name TEXT NOT NULL` | 用户填写的名称，保存后不可修改 |
| `normalized_name TEXT NOT NULL` | `NFKC → 去首尾空白 → 压缩连续空白 → casefold` |
| `scope_text TEXT NOT NULL` | 用户自由填写的范围简介，保存后不可修改 |
| `status TEXT NOT NULL DEFAULT 'active'` | `active/archived` |
| `created_at TEXT NOT NULL` | 创建时间 |
| `status_updated_at TEXT NOT NULL` | 最近状态变化时间 |

`normalized_name` 在 `active` 记录中唯一；归档方向保留原名称但释放该名称供新方向使用。历史结果通过不可变 ID 和创建时间区分同名方向。

#### `paper_direction_results`

| 字段 | 说明 |
|---|---|
| `paper_id INTEGER NOT NULL REFERENCES papers(id) ON DELETE CASCADE` | 论文 |
| `direction_id INTEGER NOT NULL REFERENCES attention_directions(id) ON DELETE RESTRICT` | 关注方向 |
| `model_decision TEXT` | `matched/possible/unmatched/failed`；NULL 表示没有模型判断 |
| `model_reason TEXT NOT NULL DEFAULT ''` | 模型分类原因 |
| `classification_evaluation_id INTEGER REFERENCES evaluations(id)` | 对应原始分类调用 |
| `classification_source TEXT` | `daily` 或 `historical_backfill` |
| `manual_decision TEXT` | NULL、`confirmed` 或 `rejected` |
| `manual_updated_at TEXT` | 最近人工判断时间 |
| `created_at / updated_at TEXT NOT NULL` | 审计时间 |

联合唯一键为 `(paper_id, direction_id)`。建议建立 `direction_id + model_decision`、`paper_id` 和 `manual_decision` 索引。

#### 复用 `evaluations` 与 `jobs`

- `evaluations` 增加 `evaluation_type='direction_classification'`；每篇论文的每次分类尝试保存一行，作为“每篇论文一次调用”的运行级事实。
- 分类评估必须保存或增加：`pipeline_job_id`、`classification_source`、`direction_snapshot_json`、`input_snapshot_json`、`input_fingerprint`、`attempt`、Prompt/Profile/模型、状态、错误码、结构化结果、原始输出和创建时间。输入快照包含当次标题、Abstract、Subjects 和类目并集，指纹用于幂等与审计。
- 每日流水线通过 `pipeline_job_id` 关联分类调用；历史补分类使用独立 `direction_backfill` job，并在 payload 中固化方向与日期范围。
- `paper_direction_results` 是便于筛选和人工处理的方向级规范化结果；模型调用、方向快照、输入和错误仍以 `evaluations` 为事实来源。

### D9. 路由与表单契约

首版沿用 `application/x-www-form-urlencoded`、POST、CSRF、同源 redirect 和 flash。字段非法返回 400 且零写入，未知论文或方向返回 404，不允许的状态转换或把归档方向用于新分类返回 409。对已经归档的方向重复提交归档请求视为幂等成功，返回正常 redirect 和“已归档”提示。

- `GET /attention-directions`：方向列表、创建表单和历史补分类入口。
- `POST /attention-directions`：字段 `name`、`scope_text`，创建后内容不可修改。
- `POST /attention-directions/<direction_id>/archive`：归档方向；不接受名称或范围更新，重复归档幂等。
- `POST /attention-directions/<direction_id>/backfill`：字段 `date_from`、`date_to` 和 `confirmed=1`；未确认时只返回预览，不创建任务。
- `POST /api/papers/<paper_id>/direction-decisions`：字段 `direction_id`、`decision=confirmed|rejected`，保存独立人工判断。

分类 Prompt 在现有 Prompt 管理中增加 `direction_classification` 类型；LLM Profile 页面增加独立的默认分类 Profile 选择。没有可用 Prompt/Profile 时，分类阶段失败并显示可操作的配置错误，不得回退成 `unmatched`。

### D10. 日志与任务状态

至少增加以下结构化事件：

- `classification.plan_created`
- `classification.skipped_no_active_directions`
- `classification.paper_started`
- `classification.paper_succeeded`
- `classification.paper_failed`
- `classification.paper_skipped_existing`
- `classification.stage_completed`
- `direction_backfill.started`
- `direction_backfill.previewed`
- `direction_backfill.completed`

分类阶段至少记录：

- 方向快照数量和 ID；
- 候选论文数、输入不完整数；
- 调用成功、失败、重试和幂等跳过数；
- 至少一个 matched、仅 possible、完全 unmatched 的论文数；
- 因分类新增的摘要评估、复用已有评估和评估失败数；
- Prompt、Profile、模型、token usage 和阶段耗时。

单篇分类失败不阻止其他论文。每日流水线中存在最终分类失败时，整体状态至少为 `partial_success`；没有启用方向导致的合法跳过仍可为 `success`。历史补分类任务使用相同的 `success/partial_success/failed/interrupted` 语义。

### D11. 验收标准

1. 用户只能创建名称和自由文本范围简介，保存后不能修改内容。
2. 归档方向后不再进入新任务快照、不可恢复，历史分类仍可回溯。
3. 无启用方向时不调用分类 LLM，并继续摘要评估全部合格论文。
4. 有启用方向时，每篇新论文只创建一个包含全部方向快照的逻辑分类任务；正常成功时只有一次物理请求，retryable 错误时最多产生三次物理请求。
5. 一篇论文可匹配多个方向，但摘要评估只创建一次。
6. `matched` 自动形成有效分类并摘要评估；`possible` 摘要评估但保持待人工确认。
7. `unmatched` 不自动摘要评估，但可手工评估和手工选择方向。
8. `failed` 不得变成 `unmatched`，重试耗尽后可查询并使任务成为部分成功。
9. 人工确认或否决不覆盖模型原始状态和原因，并按 D5.3 计算有效分类。
10. 默认列表只展示 matched/possible，unmatched/failed 可通过筛选查看。
11. 新建方向不自动触发历史任务；手动补分类必须先展示日期范围、论文数量和最大评估量。
12. 历史补分类处理范围内全部合格论文，但只判断目标新方向，不重算其他方向。
13. 补分类发现 matched/possible 且缺少摘要评估时，在同一任务中自动继续评估。
14. 重叠补分类范围、跨类目重复论文和已有成功摘要评估均不会产生重复调用或记录。
15. 分类结果契约测试覆盖未知方向、缺失方向、重复方向、未知状态、非对象 JSON 和 Provider 错误。
16. 测试不得调用真实 LLM、真实 papers.cool、生产数据库、密钥、缓存或日志。
17. 无启用方向时默认列表仍展示全部合格论文，不因没有分类结果而变空。
18. 多方向论文按 `matched > possible > failed > unmatched` 聚合；任一方向失败仍被任务汇总为部分失败。
19. 每次分类尝试都能按 evaluation ID 回溯任务、方向快照、输入快照、Prompt/Profile、尝试次数和错误。
20. 历史补分类按 `paper_categories.crawl_date` 取数、按 paper_id 去重，并正确生成范围内类目并集和输入不完整计数。
21. 自动重试耗尽后的分类或摘要失败不会被下一次日常任务无限重跑。
22. 多方向输出只有在全部方向合法时才原子写入；部分非法输出整体重试，耗尽后为全部快照方向写 failed。
23. 重复归档方向返回幂等成功；其他不允许的归档方向操作返回 409。

### D12. 首版明确延期

## 模块 E：投资主题研究备忘录（P2）

### E1. 产品结论与可行性

首版提供一个人工触发的“投资主题研究备忘录”生成器，用于把用户已经完成全文阅读和收藏筛选的多篇论文综合成一份研究底稿。它不是单篇论文卡片、每日摘要或自动投资结论，也不接入外部市场信号。

本模块复用现有论文 Metadata、收藏、投资主题、关注方向、摘要/全文评估、Prompt、LLM Profile、后台任务和手工团队数据，工程上可沿用当前 Flask、SQLite 和 JobRunner 分层。新增工作主要集中在候选集查询、不可变输入快照、多论文结构化生成、证据引用校验、版本管理和 Markdown 导出，不需要新增外部服务。

实现前必须正视以下现有代码边界：当前 `/favorites` 仍以成功全文评估列表为基础，真正的收藏语义依赖模块 B；Prompt 路由和页面目前只接受 `abstract_review/fulltext_review`；独立的 LLM Profile 数据库目前只有摘要/全文两个默认标记；JobRunner 也只显式分发抓取、摘要、全文和清理任务。模块 E 必须分别扩展这些既有入口和 migration，不能只新增页面或只靠 Prompt 约定实现。

模块 E 的关键产品原则是：

1. 用户决定研究范围和最终论文集合，模型不自行扩大样本。
2. 每次生成只使用本地已有证据，不联网补充市场、融资、开源或公司事实。
3. AI 草稿必须逐项回链到被选论文；推断与论文直接事实分开表达。
4. AI 草稿不可覆盖修改，用户的“我的投资判断”作为独立 Markdown 内容维护。
5. 生成结果按版本保存，历史版本不随收藏、分类、主题关系或最新评估变化而漂移。

### E2. 术语与证据边界

#### E2.1 术语

- **备忘录系列（Memo Series）**：同一研究主题下的一组历史版本，具有稳定 ID 和用户填写的标题。
- **备忘录版本（Memo Version）**：一次用户确认生成形成的独立记录，包括输入快照、模型配置、AI 输出、状态和该版本自己的个人判断。
- **来源模式（Source Mode）**：形成初始候选集的方法，取值为 `attention_direction`、`investment_theme` 或 `manual`。
- **确认论文集**：生成前由用户最终确认、按顺序冻结的论文 ID 集合，是该版本的事实范围。
- **证据编号**：按确认论文集顺序生成的稳定编号 `[P1]`、`[P2]` 等，只在当前备忘录版本内有效。
- **我的投资判断**：用户对某一版本单独编辑的 Markdown，不属于 AI 输出，也不默认作为后续模型输入。

#### E2.2 首版允许使用的输入

每次生成只允许读取确认论文集对应的以下本地数据：

- 论文 Metadata：标题、作者、Abstract、Subjects、类目、发布日期、arXiv ID，以及已经入库的 papers.cool 社区指标；
- 用户选择的一个关注方向的名称与范围简介快照，或一个投资主题的名称与说明快照；手工模式不要求来源实体；
- 每篇论文在确认时最新一次成功的摘要评估，可为空；
- 每篇论文在确认时最新一次成功的全文评估，必须存在；
- 收藏状态、论文与投资主题关系、有效关注方向分类；
- 与确认论文关联且已经人工确认的作者、机构/企业和团队备注；没有团队数据不阻塞生成。

下列内容不得在首版自动读取或作为“已经核验的事实”写入：

- 原始 PDF、实时网页或开放互联网搜索结果；
- 新接入的 OpenAlex、Semantic Scholar、GitHub、Hugging Face、融资数据库、工商或市场数据；
- 未经人工确认的作者、机构或企业推测；
- 其他备忘录的个人投资判断。

papers.cool 社区指标只能作为“社区关注度”证据，不能直接推导投资价值。由于首版没有外部市场事实，“中国市场相关性”只能表达为基于技术特征的待验证假设和尽调问题，不能声称已经验证市场规模、竞争格局、融资情况或监管状态。

### E3. 两种选论文模式

两种模式只决定初始候选集，最终均进入同一确认和生成流程。所有可选论文必须在提交时仍处于 `paper_dispositions.decision='favorite'`，并满足模块 B 的历史成功全文评估资格。

#### E3.1 模式 A：按关注方向或投资主题预选

用户每次只能选择以下一种来源：

1. **一个关注方向**：初始候选集为“当前收藏”与该方向“当前有效分类”的交集。有效分类沿用 D5.3：模型 `matched` 且未被人工否决，或 `possible` 已被人工确认，或用户手工确认属于该方向。仍待确认的 `possible` 不进入候选集。
2. **一个投资主题**：初始候选集为“当前收藏”与用户手工加入该投资主题的论文交集。主题归档后仍可用于历史查看，但不能创建新的来源备忘录版本；已有版本不受影响。

创建系列或新版本时来源方向/主题必须仍为 active；归档来源只影响后续生成资格，不影响历史版本查看和导出。

预选页必须展示：

- 来源名称和范围简介/主题说明；
- 来源下论文总数、其中已收藏数、最终预选数；
- 因未收藏、待确认 `possible`、人工否决或缺少成功全文评估而未进入候选集的数量；
- 每篇候选论文的全文评分、收藏时间、方向和主题标签。

用户可以在生成前移除预选论文，也可以从其他收藏论文中手工追加。追加论文不要求属于所选来源，但 UI 必须标记为“人工追加”，避免让来源标签造成错误归因。移除只影响当前备忘录版本，不改变收藏、方向或主题数据。

#### E3.2 模式 B：从收藏列表手工选择

用户从全部收藏论文中勾选任意一组论文，可跨多个关注方向和投资主题，不要求设置来源实体。至少支持按以下字段筛选和排序：

- 标题或 arXiv ID；
- 收藏时间；
- 关注方向；
- 投资主题；
- 已人工确认的作者或机构/企业；
- 最新成功全文评估评分。

首版不提供多个方向/主题的并集、交集条件构建器。需要跨来源组合时统一使用手工选择模式。

### E4. 统一确认与生成流程

```text
选择来源模式
  → 系统形成初始候选集或展示收藏列表
  → 用户增加、移除并排序论文
  → 系统重新校验收藏与全文资格
  → 锁定论文、评估、来源和模型配置快照
  → 预估上下文与 token
  → 用户确认生成
  → 后台执行一次结构化 LLM 调用
  → 校验证据引用和输出契约
  → 保存不可变 AI 草稿版本
  → 用户单独填写“我的投资判断”
```

生成前必须满足以下条件：

1. 最终论文集至少有 1 篇，且论文 ID 去重；展示顺序由用户确认并决定 `[P<n>]` 编号。
2. 服务端不得信任页面提交的标题、评估文本或来源说明，必须按提交的论文 ID 和来源 ID 从数据库重新读取并校验。
3. 每篇论文必须仍为收藏，且历史中至少有一次成功全文评估；不满足时整次提交返回 409，指出需要重新确认的论文，不创建任务。
4. 系统锁定每篇论文当时最新一次成功全文评估 ID，以及存在时最新一次成功摘要评估 ID；“最新”复用现有查询规则，按成功记录的 `evaluations.created_at DESC, id DESC` 稳定排序。
5. 方向/主题名称和说明、论文 Metadata、结构化评估、人工确认团队信息、Prompt、Profile、模型及生成参数均保存快照。
6. 生成后的事实来源是确认论文 ID、评估 ID 与输入快照，不是动态查询当前主题或方向成员。
7. 来源实体之后被改名、归档，论文之后被取消收藏、改分类、移出主题或重新评估，都不得修改历史版本。
8. 系统在创建任务前按所选模型上下文限制做 token 估算；预计超限时不调用模型，提示用户减少论文或选择上下文更长的 Profile。

首版不自动分块、分层摘要或合并多个模型调用。每次用户确认生成只允许一次物理 LLM 调用；Provider 错误、上下文超限或无效结构化输出不会在后台静默追加调用。用户可以显式重试，重试会基于冻结或重新确认的输入创建一个新版本，失败记录仍保留。

### E5. AI 输出结构与证据契约

#### E5.1 固定章节

AI 草稿至少包含以下章节，页面和 Markdown 导出保持相同顺序：

1. 核心结论；
2. 覆盖的技术范围；
3. 主要技术路线；
4. 多篇论文的共识与分歧；
5. 关键技术变化；
6. 潜在产品形态与创业切入点；
7. 可能受益的产业链环节；
8. 关键作者、机构与团队；
9. 中国市场相关性假设；
10. 技术与商业化风险；
11. 反证、证据缺口与不确定性；
12. 下一步尽调问题；
13. 论文证据索引。

章节可明确写“证据不足”，但不得删除。Prompt 可以调整分析侧重点和语言风格，不能移除固定章节、证据字段或免责声明。

#### E5.2 结构化输出

LLM 返回的 v1 对象必须严格符合以下逻辑结构；正式实现时把同等约束固化为仓库内可版本化、可单元测试的 JSON Schema，并将 Schema 版本写入备忘录快照：

```json
{
  "schema_version": "investment_memo.v1",
  "language": "zh-CN",
  "sections": {
    "core_conclusions": { "status": "supported", "summary": "...", "claims": [] },
    "technical_scope": { "status": "supported", "summary": "...", "claims": [] },
    "technical_routes": { "status": "supported", "summary": "...", "claims": [] },
    "consensus_and_disagreements": { "status": "supported", "summary": "...", "claims": [] },
    "technical_changes": { "status": "supported", "summary": "...", "claims": [] },
    "product_and_startup_opportunities": { "status": "supported", "summary": "...", "claims": [] },
    "value_chain_beneficiaries": { "status": "supported", "summary": "...", "claims": [] },
    "key_people_and_organizations": { "status": "supported", "summary": "...", "claims": [] },
    "china_market_hypotheses": { "status": "insufficient_evidence", "summary": "...", "claims": [] },
    "risks": { "status": "supported", "summary": "...", "claims": [] },
    "counterevidence_and_gaps": { "status": "supported", "summary": "...", "claims": [] }
  },
  "diligence_questions": [
    { "question_text": "...", "reason": "...", "evidence_refs": ["P1"] }
  ]
}
```

每个 `claims` 元素固定为：

```json
{
  "claim_text": "...",
  "claim_type": "paper_fact",
  "evidence_refs": ["P1"],
  "reasoning": "..."
}
```

Schema 规则固定如下：

- 顶层、11 个 `sections` key、每个 Section 的 `status/summary/claims` 以及 `diligence_questions` 都是必填项，不允许额外字段或 `null`。
- `schema_version` 只能为 `investment_memo.v1`，`language` 首版只能为 `zh-CN`。
- Section `status` 只能为 `supported/insufficient_evidence`；`summary` 去空白后不能为空。
- `supported` Section 至少包含一条 Claim；`insufficient_evidence` 可以是空 Claim 数组，但 `summary` 必须说明缺少的证据。
- Claim 的 `claim_type` 只能为 `paper_fact/cross_paper_inference/insufficient_evidence`；所有字符串去空白后不能为空，所有数组必须显式返回。
- JSON 中引用写作 `P1`，服务端渲染为 `[P1]`。编号必须在当前版本范围内、数组内去重，并保持用户确认的论文顺序语义。
- `diligence_questions` 至少有一项；`question_text/reason/evidence_refs` 必填，前两项非空，证据缺口型问题允许 `evidence_refs=[]`。
- `china_market_hypotheses` 中不得出现 `paper_fact` 类型，只能使用 `cross_paper_inference/insufficient_evidence`。

固定免责声明和第 13 章论文证据索引不交给模型生成：服务端在 Schema 校验后，根据冻结快照确定性追加到规范化 `result_json` 和 Markdown。论文标题、arXiv ID、评估 ID 与本地链接不得采用模型复述值。Provider 原文单独进入 `raw_output`。

证据规则如下：

1. `paper_fact` 必须至少引用一篇直接支持该事实的论文。
2. `cross_paper_inference` 必须引用形成推断的论文，不得包装成论文作者的直接结论。
3. `insufficient_evidence` 可以引用暴露缺口的论文，也可以为空，但必须明确说明缺少什么证据。
4. 所有引用必须落在当前确认论文集，未知编号、越界编号或引用已移除论文均视为结构化输出失败。
5. 关键作者、机构与团队只能使用论文 Metadata 或人工确认实体；推测性归属必须进入证据缺口，不能写成事实。
6. 论文证据索引至少展示编号、标题、arXiv ID、所用摘要/全文评估 ID，以及打开本地论文详情的链接。

服务端校验只能确认章节、字段和引用编号合法，不能机械证明某个引用在语义上真正支持结论。UI 应称其为“论文引用”而不是“已核验事实”；语义一致性通过固定 Prompt、离线样例测试和用户阅读判断控制，并在外部事实核验能力上线前始终保留上述限制。

每份 AI 草稿顶部和导出文件中必须包含固定声明：

> 本备忘录仅基于用户确认纳入的论文、系统已有评估和人工记录生成，未进行开放互联网、市场、融资、公司经营或监管信息核验；其中商业机会和中国市场相关性属于待验证研究假设，不构成投资建议。

### E6. 版本、编辑与导出

1. 用户首次生成时创建一个备忘录系列和版本 1。系列标题、来源模式和来源实体在创建后不可修改：方向系列始终绑定同一个 `direction_id`，主题系列始终绑定同一个 `theme_id`，手工系列始终保持 `manual`。需要更换来源时新建系列，不把不同研究对象混进同一版本时间线。
2. 在现有系列中再次生成创建下一个版本，不覆盖旧版本；每一次已创建的生成尝试都占用一个递增版本号，包括 `failed/interrupted`，版本号不得回收或重排。主题名称/说明后续可编辑，但每个版本保存生成时快照。
3. 成功版本的来源、论文顺序、评估引用、输入快照、Prompt/Profile/模型快照、AI JSON 和渲染 Markdown 均不可编辑。
4. 每个版本拥有独立的“我的投资判断”Markdown，用户可以持续编辑；该字段的修改不改变 AI 草稿和生成时间。
5. 创建新版本时，用户可选择“复制上一版本的我的投资判断作为初始文本”。复制只发生在用户编辑区，不默认发送给 LLM。
6. 失败版本保留状态、冻结输入、错误类型和任务 ID，便于审计费用与排障；用户显式重试时先回到确认页并预填旧版本论文/配置，仍须按当前收藏与全文资格重新校验，确认后创建新版本。
7. 系列列表展示不可变标题与来源、最新成功版本、论文数、创建时间和最近更新时间；首版允许归档系列，不提供恢复、重命名、换来源、硬删除和跨系列合并。
8. 每个成功版本可导出单一 Markdown 文件，顺序为固定声明、AI 草稿、我的投资判断、论文证据索引和生成配置摘要。
9. 导出读取该版本已保存的 Markdown 与快照，不在导出时重新调用模型或动态重算证据。

### E7. Prompt、Profile 与生成配置

- 在现有 Prompt 管理中增加独立类型 `investment_memo`，不得复用摘要或全文评估 Prompt 类型。
- LLM Profile 设置增加“默认研究备忘录 Profile”；生成确认页允许用户为本次选择其他可用 Prompt/Profile。
- 版本必须保存 Prompt ID、Prompt 内容快照、Profile ID、Provider、模型名、温度、最大输出 token 和其他实际生效参数。
- 固定系统指令负责 JSON Schema、章节、证据编号和免责声明；用户可编辑 Prompt 只负责分析侧重点，不能覆盖固定安全与输出契约。
- 输入使用结构化全文评估及摘要评估，不直接塞入原始 PDF 或转换后的整篇 Markdown。
- 生成前展示论文数、预计输入 token、模型上下文上限和预计可用输出空间；估算值不是费用承诺。
- 如果缺少可用 Prompt/Profile、Profile 已归档或模型上下文不足，提交前阻止生成并给出可操作错误，不回退到其他模型。

### E8. 数据模型

#### `investment_memo_series`

| 字段 | 说明 |
|---|---|
| `id INTEGER PRIMARY KEY` | 备忘录系列 ID |
| `title TEXT NOT NULL` | 用户填写的系列标题 |
| `source_mode TEXT NOT NULL` | 创建后不可变：`attention_direction/investment_theme/manual` |
| `source_direction_id INTEGER REFERENCES attention_directions(id) ON DELETE SET NULL` | 方向系列的固定来源 |
| `source_theme_id INTEGER REFERENCES investment_themes(id) ON DELETE SET NULL` | 主题系列的固定来源 |
| `status TEXT NOT NULL DEFAULT 'active'` | `active/archived` |
| `created_at / updated_at TEXT NOT NULL` | 审计时间 |

系列标题限制 1～120 个字符。使用 `CHECK` 约束保证三个来源模式与两个来源 ID 的空值组合合法。标题和来源创建后不可修改；归档后仍可查看和导出历史版本，但不能新增版本。来源实体被归档或删除引用变为 NULL 后也不能新增版本；历史版本继续使用快照。

#### `investment_memo_versions`

| 字段 | 说明 |
|---|---|
| `id INTEGER PRIMARY KEY` | 版本 ID |
| `series_id INTEGER NOT NULL REFERENCES investment_memo_series(id) ON DELETE RESTRICT` | 所属系列 |
| `version_no INTEGER NOT NULL` | 系列内递增版本号 |
| `previous_version_id INTEGER REFERENCES investment_memo_versions(id)` | 上一版本，可为空 |
| `idempotency_key TEXT NOT NULL UNIQUE` | 防止同一次页面提交重复创建 |
| `source_mode_snapshot TEXT NOT NULL` | 创建版本时复制系列来源模式 |
| `source_entity_id_snapshot INTEGER` | 方向/主题原始 ID 快照；手工模式为空，不设外键 |
| `source_name_snapshot TEXT NOT NULL DEFAULT ''` | 来源名称快照；手工模式为空 |
| `source_scope_snapshot TEXT NOT NULL DEFAULT ''` | 方向范围或主题说明快照；手工模式为空 |
| `status TEXT NOT NULL` | `pending/running/success/failed/interrupted` |
| `job_id INTEGER REFERENCES jobs(id)` | 后台任务 |
| `prompt_id INTEGER REFERENCES prompts(id) ON DELETE SET NULL` | 使用的 Prompt ID，允许后续配置归档 |
| `profile_id INTEGER` | 使用的 LLM Profile ID；Profile 在独立数据库中，不能建立跨库外键 |
| `prompt_snapshot TEXT NOT NULL` | 实际生效的 Prompt 内容快照 |
| `profile_snapshot_json TEXT NOT NULL` | Provider、模型和生成参数快照；严禁包含 API key、加密 key 引用值或认证头 |
| `provider / model TEXT NOT NULL` | 便于列表、审计和统计的实际 Provider 与模型 |
| `input_snapshot_json TEXT NOT NULL` | 来源、团队数据、整体参数及输入摘要快照 |
| `estimated_input_tokens INTEGER` | 提交前估算值 |
| `input_tokens / output_tokens INTEGER` | Provider 返回的实际用量，未提供时为空 |
| `result_json TEXT` | 校验通过的 AI 结构化结果，成功时必填 |
| `rendered_markdown TEXT` | 从结构化结果渲染的不可变 AI 草稿 |
| `raw_output TEXT` | Provider 原始文本，仅用于失败诊断和审计，不作为成功内容渲染 |
| `personal_judgment_markdown TEXT NOT NULL DEFAULT ''` | 当前版本可编辑的个人判断 |
| `personal_judgment_updated_at TEXT` | 个人判断最近更新时间 |
| `error_code TEXT` | 可统计的失败类型 |
| `error_message TEXT` | 经过脱敏的失败摘要，不保存密钥和敏感请求头 |
| `created_at TEXT NOT NULL` | 版本创建时间 |
| `started_at / finished_at TEXT` | 生成开始和结束时间 |

联合唯一键为 `(series_id, version_no)`。创建版本时服务层必须校验来源快照与系列身份相同。成功后所有 AI 与输入字段不可更新，只有个人判断、个人判断更新时间以及系列归档状态可变。

#### `investment_memo_version_papers`

| 字段 | 说明 |
|---|---|
| `memo_version_id INTEGER NOT NULL REFERENCES investment_memo_versions(id) ON DELETE CASCADE` | 版本 |
| `paper_id INTEGER REFERENCES papers(id) ON DELETE SET NULL` | 当前论文引用；论文被清理后允许为空 |
| `paper_arxiv_id_snapshot TEXT NOT NULL` | 稳定论文标识快照 |
| `display_order INTEGER NOT NULL` | 用户确认顺序，也是 `[P<n>]` 编号依据 |
| `selection_origin TEXT NOT NULL` | `preselected/manual_selected/manual_added` |
| `abstract_evaluation_id INTEGER REFERENCES evaluations(id) ON DELETE SET NULL` | 锁定的成功摘要评估，可为空 |
| `fulltext_evaluation_id INTEGER REFERENCES evaluations(id) ON DELETE SET NULL` | 锁定的成功全文评估，创建时必填 |
| `paper_snapshot_json TEXT NOT NULL` | Metadata、评估结果及人工团队记录快照 |

联合唯一键为 `(memo_version_id, display_order)` 和 `(memo_version_id, paper_arxiv_id_snapshot)`。即使源论文或评估后续被清理，历史备忘录仍通过快照保留当时证据；UI 同时标明当前源记录是否仍存在。

建议建立 `investment_memo_series(status, updated_at)`、`investment_memo_versions(series_id, version_no)`、`investment_memo_versions(status, created_at)` 和 `investment_memo_version_papers(memo_version_id, display_order)` 索引。候选列表、评估锁定和团队实体必须批量查询，禁止逐论文 N+1。

### E9. 路由与页面契约

沿用现有服务端 HTML、`application/x-www-form-urlencoded`、POST、CSRF、同源 redirect 和 flash。未知论文/系列/来源返回 404；字段非法返回 400 且零写入；资格变化、归档来源或归档系列返回 409。

- `GET /investment-memos`：系列列表及其最新成功版本。
- `GET /investment-memos/new`：选择来源模式、来源实体、论文和生成配置。
- `POST /investment-memos/preview`：按来源和筛选条件返回候选与 token 预估，不创建 Job、不调用 LLM。
- `POST /investment-memos`：新系列提交标题、来源、按顺序的 `paper_ids`、Prompt/Profile 和 `idempotency_key`；已有系列提交 `series_id`、论文、配置和 key，不接受新的标题或来源。服务端重新校验后创建版本与后台任务。
- `GET /investment-memos/<series_id>`：版本时间线。
- `GET /investment-memos/<series_id>/versions/<version_id>`：版本详情、AI 草稿、个人判断和证据索引。
- `POST /investment-memos/<series_id>/versions/<version_id>/personal-judgment`：只保存该版本个人判断 Markdown。
- `GET /investment-memos/<series_id>/versions/<version_id>/new-version`：从旧版本回到确认页，可选复制论文集、配置和个人判断；不得直接调用模型。
- `POST /investment-memos/<series_id>/archive`：归档系列，重复归档幂等。
- `GET /investment-memos/<series_id>/versions/<version_id>/export.md`：导出已保存的单一 Markdown。

预览请求不锁定资格。只有 `POST /investment-memos` 成功创建版本时才冻结快照。详情页必须同时展示来源模式、来源快照、论文数、版本号、生成时间、Prompt/Profile/模型、任务状态和固定免责声明。

### E10. 任务、幂等、失败与日志

- 增加 `investment_memo_generation` Job 类型；任务 payload 保存版本 ID，不重复保存密钥或完整敏感 Profile。
- 版本、论文快照、Job 和 `job_id` 回填必须在主库同一事务中完成：先取得版本 ID，再创建只含版本 ID 的 Job 并回填关联；任一步失败均整体回滚。
- 状态从 `pending → running → success/failed`；服务启动时遗留的 `pending/running` 按现有恢复规则转为 `interrupted`。
- 同一 `idempotency_key` 重复提交返回原版本和 Job，不创建第二个调用；用户主动新建版本必须获得新的 key。
- 一次生成中的任何论文失去资格会使创建事务整体回滚，不允许悄悄少用部分论文。
- Job 启动后只读取版本快照。运行期间收藏、方向、主题、团队或评估数据变化不影响本次输入。
- 生成终态必须在同一主库事务中同步更新版本和 Job；启动恢复流程应把不一致的非终态记录归并为 `interrupted`，不得出现版本显示成功而 Job 永久 running 的状态。
- Provider、认证、上下文、JSON 解析、Schema、未知证据编号和数据库错误必须使用不同错误码；失败版本不得出现看似成功的部分 Markdown。
- 如果 Provider 已返回但进程在持久化结果前中断，系统无法保证外部调用 exactly-once。版本和 Job 标记为 `interrupted/external_outcome_unknown`；系统不自动重调，用户确认重试后才创建新版本，且 UI 明示可能产生过一次费用。
- 用户个人判断的保存不进入生成 Job，不触发 LLM；渲染和导出 Markdown 时必须转义危险 HTML。

至少增加以下与生成 Job 关联的结构化事件：

- `investment_memo.version_created`
- `investment_memo.generation_started`
- `investment_memo.generation_succeeded`
- `investment_memo.generation_failed`

生成完成事件至少记录版本 ID、来源模式、论文数、Prompt/Profile/模型、输入/输出 token、耗时和终态；不得记录 API key、完整认证头或原始 PDF。

预览不创建 Job，因此不写 `job_events`；个人判断保存和导出也不是后台任务，只进入普通运行日志且不得记录正文。产品指标直接从版本、论文关系和任务结果统计，不依赖解析文本日志。

### E11. 验收标准

1. 用户可从一个关注方向或一个投资主题形成收藏论文初始候选集，也可从收藏列表完全手工选择。
2. 方向模式只预选有效 classified 且已收藏的论文，待确认 `possible` 和人工否决结果不进入。
3. 主题模式只预选同时收藏且被手工加入该主题的论文。
4. 用户可在预选后移除论文或追加其他收藏论文，追加项被明确标记。
5. 手工模式可跨方向和主题选择，并支持 E3.2 规定的筛选。
6. 未收藏、没有历史成功全文评估、未知或重复的论文不能进入生成任务；任一失败时零任务、零版本写入。
7. 预览不调用 LLM，确认时重新校验并锁定论文顺序、最新成功评估和全部输入快照。
8. 后续取消收藏、调整方向/主题、修改主题说明或产生新评估不会改变历史版本。
9. 每次确认生成只产生一个物理 LLM 调用；重复页面提交由 idempotency key 返回同一版本。
10. 输入预计超过模型上下文时在调用前阻止生成；首版不自动分块或多调用合并。
11. LLM 输出缺章节、类型非法、JSON 非对象、引用未知 `[P<n>]` 或缺少必要证据时版本为 failed，不保存部分 AI 草稿。
12. 成功 AI 草稿包含全部固定章节、固定免责声明和可回到本地论文详情的证据索引。
13. 中国市场、商业机会和产业链判断被标为假设或推断，不出现伪造的外部市场事实。
14. AI 草稿和输入快照不可编辑；每个版本的个人判断可独立编辑且不触发 LLM。
15. 新版本可选复制上一版本个人判断，但复制内容不默认进入模型输入，旧版本保持不变。
16. Provider 或结构化输出失败记录错误和任务 ID；只有用户明确重试才创建新版本和新调用。
17. 成功版本可导出包含 AI 草稿、个人判断、证据索引和生成配置摘要的 Markdown，导出不重新生成。
18. 候选集、评估锁定和团队数据使用批量查询，性能测试或查询计数证明不存在按论文 N+1。
19. 数据库测试覆盖版本号、来源 `CHECK`、顺序/论文唯一键、幂等 key、快照保留和系列归档。
20. 路由与服务测试覆盖 CSRF、未知/归档实体、资格竞争、重复提交、上下文超限、失败恢复和 Markdown 转义，且不访问真实 LLM、网络、生产数据库、缓存、日志或密钥。
21. JSON Schema 契约测试覆盖全部必填章节、额外字段、`null`、Section 状态与空 Claims、Claim 类型、证据编号、尽调问题和中国市场类型限制。
22. 已有系列拒绝修改标题、来源模式或来源实体；归档系列或归档来源不能新增版本，历史成功/失败版本仍可查看，成功版本仍可导出。

### E12. 首版明确延期

- 外部学术、开源、融资、公司、市场、监管和新闻信号。
- 系统自动发现趋势、自动创建关注方向或自动选择投资主题。
- 定时或无人工确认地自动生成备忘录。
- 多方向、多主题的可视化并集/交集规则构建器。
- 原始 PDF/全文 Markdown 直接作为多论文生成输入。
- 自动分块、多阶段 Map-Reduce、多个模型交叉评审或事实核验 Agent。
- 把“我的投资判断”自动作为模型上下文、自动改写个人结论或自动形成投资决策。
- 富文本协同编辑、评论、权限、分享链接、Word/PDF 导出和外部知识库同步。

### E13. 产品指标

- 每周/月创建的备忘录系列数、成功版本数和生成成功率。
- 两种选论文模式的使用占比、每份备忘录的论文数和人工增删比例。
- 从首次收藏到进入备忘录的转化率与时间。
- 有填写“我的投资判断”的成功版本占比，以及用户后续创建新版本的比例。

## 7. 总体数据迁移与兼容性

1. 主业务库的新增表和索引放入现有 `_init_db_once()` 的幂等 `CREATE TABLE IF NOT EXISTS` / `CREATE INDEX IF NOT EXISTS` 初始化路径；LLM Profile 默认分类/备忘录标记属于独立 Profile 数据库，必须在 `init_llm_profiles_db()` 及兼容迁移中增加。两者均不依赖手工 SQL，不通过破坏性重建现有业务表实现。
2. 历史成功全文评估论文默认保持“未处理”“未加入主题”“未跟踪团队”；历史论文不会因创建关注方向而自动补分类。
3. 不读取或修改仓库外的账号、通讯录或投资组合数据。
4. 归档主题、作者和机构时保留历史关系；列表默认隐藏归档对象，但详情可回溯。
5. 现有论文数据导出后续应增加个人决策、投资主题和团队字段；模块 E 的备忘录 Markdown 导出使用独立路由和不可变版本快照，不与论文批量导出混用。
6. 当前生产数据库迁移前应做文件级备份，并在临时数据库上验证向前迁移和重复启动幂等性。
7. 外键行为固定为：删除论文级联删除个人决策、主题关系、团队跟踪和论文方向结果；主题、作者、机构和关注方向首版禁止硬删除并按各模块规则归档。备忘录属于历史研究输出，论文或评估被清理时使用 `ON DELETE SET NULL` 保留版本快照，不级联删除备忘录。
8. 新增备忘录表后，不为历史收藏自动创建系列或版本；只有用户确认生成才写入。
9. 迁移验收必须覆盖空数据库、仅有旧 schema 的数据库和连续执行两次初始化三种场景，并检查新增唯一键、`CHECK`、索引和外键均生效。

最终应能回答以下业务问题：
