# 全量采集与摘要评估：首次性能基准

测量日期：2026-10-07。Python 3.12.2，SQLite 3.43.1，Windows 11。

## 结论

本次真实源站测试抓取 10 个选定类目的峰值日数据，2,119 条类目记录去重后为 1,475 篇论文，完整性检查全部通过。6 并发抓取与解析耗时 93.917 秒，随后串行写入临时数据库耗时 0.135 秒。当前规模下，采集能够在本次测量中于约两分钟内完成。

模拟模型的真实应用流水线测试表明，提高 LLM 并发有明显收益：同一负载下，4、8、12 并发分别耗时 207.432、118.693、83.511 秒，均全部成功。8 并发比 4 并发缩短 42.8%，12 并发缩短 59.7%。这些结果验证程序吞吐，不代表真实供应商响应速度或限流额度。

## 测量方法与隔离

- 真实源站：固定抓取 `2026-10-06`，类目为 cs.AI、cs.CL、cs.CV、cs.HC、cs.IR、cs.LG、cs.RO、cs.SE、eess.IV、stat.ML。共享 HTTP client，6 类目并发，使用生产全量抓取及完整性检查代码。先完成全部抓取，再将结果写入临时 SQLite；不运行 JobRunner 或 LLM。
- 离线流水线：调用生产 `JobRunner._run_job`，覆盖任务状态、进度写入、全量抓取解析、入库、方向分类、摘要评估、调用账本及最终统计。抓取与 LLM 传输均使用 `httpx.MockTransport`，socket 连接被禁止。
- 离线数据：同样的 2,119 条类目记录，构造 1,500 篇唯一论文；一个关注方向；固定 20% 入选摘要，即 1,500 次分类和 300 次摘要请求。摘要、判断、输出及 token 使用量均为合成数据，不评估模型质量或费用。
- 模拟等待：分类每请求 0.2 秒，摘要每请求 1 秒，采用实际墙钟等待，不使用压缩时间或真实模型延迟外推。模拟抓取不添加网络等待。
- 每个用例使用全新临时数据库，初始化、配置及 HTML 构造不计入任务耗时。没有启动应用 runtime、scheduler 或后台 worker。
- 未打开正式数据库、正式 profile 或本地密钥，未下载 PDF、生成全文缓存或调用付费模型。测试临时目录由测试上下文回收。
- 每种场景仅测一次。没有控制机器上所有其他进程，没有模拟历史数据库、追赶多日数据或人工任务排队。阶段 p50/p95 的样本口径可在 JSON 中检查，不能当作多次端到端运行的分位数。

真实源站与模拟流水线是两个独立测试；不能将两组耗时直接相加并称为真实端到端实测。

整体完成时间接近最慢 cs.LG 类目的时间，说明本次关键路径在单个大类目的 HTTP 响应。继续提高类目并发不一定能缩短这条关键路径；合并重复 HTML 解析有确定收益，但本次收益量级小于 HTTP 等待。

## 模拟流水线结果

原始记录：[PIPELINE_BENCHMARK.json](PIPELINE_BENCHMARK.json)。

| 场景 | LLM 并发 | 模拟分类 / 摘要等待 | 完整任务耗时 | 结果 |
|---|---:|---|---:|---|
| 本地开销 | 4 | 0 / 0 秒 | 62.560 秒 | 成功 |
| 带模型等待 | 4 | 0.2 / 1 秒 | 207.432 秒 | 成功 |
| 带模型等待 | 8 | 0.2 / 1 秒 | 118.693 秒 | 成功 |
| 带模型等待 | 12 | 0.2 / 1 秒 | 83.511 秒 | 成功 |
| 429 重试恢复 | 4 | 0.2 / 1 秒 | 224.370 秒 | 60 次首发 429 全部恢复 |

不加模型等待时，分类阶段耗时 48.113 秒，摘要阶段耗时 12.607 秒；任务生成 1,800 条评估、1,800 条调用账本及 3,666 条事件。这些是整个阶段的本地开销，不能解释为单次数据库操作延迟或 SQLite 写锁等待时间。

同日重复运行耗时 11.037 秒，新增 LLM 请求为 0，状态成功。重复执行仍会重新抓取并检查记录，并非零成本。

429 场景按论文编号每 50 篇注入一次首发失败。分类首发失败 30 次（2%），这些论文均属于入选摘要的编号，因此摘要首发失败也是 30 次（10%）；合计 60 次。保留实际重试代码，首次退避为 1 秒加 0.5 秒固定 jitter。最终 1,800 次成功评估，物理请求与调用账本均为 1,860 条，恢复前失败评估记录 60 条，没有终态失败。相比无重试的 4 并发用例增加 16.938 秒；单次运行差值包含本地开销波动及等待重叠，不能当作每次 429 的固定成本。该场景没有模拟持续配额耗尽或重试风暴。

## 验证与优化方向

1. 基准检查唯一论文、类目关联、分类与摘要成功数、20 次模拟抓取请求、物理 LLM 请求与调用账本数量一致，以及同日重复运行零新增 LLM 请求。
2. 后置断言确认带等待的并发场景实际同时进行的模拟请求分别达到 4、8、12；429 场景的分类及摘要各重试 30 次，全部恢复，数量与失败记录、物理请求账本一致；应用及基准脚本源码哈希均未变化。没有流水线系统错误；未单独测量 SQLite 写锁等待。
3. 先以 8 并发作为真实模型小样本验证的候选，记录真实分类/摘要 p50、p95、RPM、TPM、429 和超时，再决定是否使用 12 并发。测试没有修改正式并发设置。
4. 本次本地开销约一分钟，当前不应先增加 SQLite 写线程。若后续需要进一步减少开销，应测量各类 claim、事件、调用账本和结果事务，再减少重复查询或合并可合并的非关键写入。
5. 保留方向门控。真实摘要入选比例尚未测量；若入选率高于本次假设，摘要阶段将更长。未启用关注方向时，全部候选会进入摘要评估。

尚不能验收“真实模型全量评估 30 分钟内完成”：本次没有真实模型调用、限流测量或完整真实流水线计时，也没有测量单 worker 下人工任务的排队体验。
