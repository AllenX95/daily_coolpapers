# S0–S5 架构优化发布与验收说明

日期：2026-10-01。S6 隔离演练结果见 `S6_RECOVERY_REPORT.md`；阶段实施与验收结论见 `PRD_架构稳定性与性能优化.md` 第 15–21 节。本说明不表示已部署生产。

## 交付行为

- 同一数据工作区仅允许运行一个业务运行时；取得锁后才执行初始化、任务恢复与清理，退出时等待任务线程后释放锁。
- 每日时段持久化，晚启动有限补跑、同日合并、活动任务暂缓；旧任务 key 保留兼容，不自动重调结果未知的调用。
- 收藏、全文库及备忘录候选按 SQL 分页；备忘录跨页选择使用版本化草稿，预览不创建模型任务，确认后冻结原有版本快照。
- 研究模型请求逐物理 attempt 记录，缺失 usage 显示未知；响应记账失败禁止额外请求。Profile 连接测试、价格与费用系统不纳入。
- 投资主题与研究对象／团队跟踪数据库职责拆到独立模块，保留 `db.py` 接口、异常及事务边界；URL 和现有页面流程继续兼容。

## 发布操作

1. 保存当前完整代码包和依赖版本。包括所有新增 Python 模块与模板，不能只复制已跟踪文件的 diff；当前改动尚未提交。停止旧进程，确认工作线程结束、工作区锁释放，不运行新旧两套调度／写入层。
2. 由实际运行配置确定主库和 Profile 库路径，默认分别位于 `data/daily_coolpapers.sqlite3`、`instance/llm_profiles.sqlite3`。在停机状态分别使用 SQLite backup API 生成一致性备份；不要只复制可能仍有 WAL 的主库文件。两库备份不是跨库原子事务，停机是获得一致工作区快照的前提。
3. 保存本地解密材料。Fernet 需要 `instance/fernet.key`；DPAPI 需要原 Windows 用户／系统上下文，复制 key 文件不能代替 DPAPI 恢复。密钥、数据库及生产日志只在用户安全位置保管，不进入仓库或交付报告。
4. 在隔离工作区用匹配代码验证备份可读取且 Profile 可解密；随后在真实工作区按既有启动方式启动。初始化、Profile 迁移、旧调度关联迁移和中断恢复在运行时锁内执行，失败即停止启动。
5. 核对设置、论文／收藏／主题、历史备忘录和任务详情；在途未知结果保持终态，不因升级自动补发。查看本地启动日志后再恢复日常使用。初次迁移的耗时及空间参考 S3 报告，生产规模可能不同。

## 回退操作

优先停机后切换到验证过、保留 S1–S4 保护的匹配 S4 整套代码，保留升级后的数据库及新增历史记录；本轮仅演练 S5→S4 兼容回退。`db.py` 与其依赖必须来自同一包，不能在生产只替换单文件。仓库忽略的临时 S4 材料是演练输入，不是正式回退包。

若目标代码与现有数据库不兼容，则停机、另存当前两库与本地材料，再恢复同一备份时点的两库和匹配代码。备份后新增／修改的论文、判断、草稿、备忘录、任务及调用记录会丢失，须事先明确时间范围并保留当前库供核对。备份不会撤销已发送的 Provider 请求或费用；恢复后在途状态仍按未知处理，禁止自动重调。

不删除新表、列、触发器或历史调用记录。更早版本若缺少单实例及未知结果禁止重调保护，不能据本次演练作为安全回退方案；关闭自动调度也不能替代所有手工／后台恢复保护。
