## F1：北京时间选样窗口整体提前 8 小时

**情况及触发条件**：运行环境为 UTC+08:00，论文经标准入库函数保存为无时区偏移的本地时间。探索查询却将该值与转换后的 UTC 窗口比较。

**复现步骤**：

1. 在隔离库固定探索日期为北京时间 2026-10-08。
2. 用标准 `db.upsert_papers` 入库两篇符合其他选样条件的论文，首次入库时间分别为本地无偏移字符串 `2026-09-30 20:00:00`、`2026-10-07 20:00:00`。
3. 打开 `/direction-exploration`，检查页面日期及入样论文。

**预期**：页面窗口为 10-01 至 10-07，仅第二篇入样。对应北京时间半开区间为 `[10-01 00:00, 10-08 00:00)`。

**实际**：页面日期正常，实际仅第一篇入样。比较窗口提前 8 小时。

**问题与影响**：周报呈现的日期与实际数据范围不一致，系统性漏掉结束日最后 8 小时并纳入起始日前的 8 小时。已有测试使用带 UTC 偏移的时间，未覆盖实际写入格式。

**定位线索**：`daily_coolpapers/db.py:89` 的 `now_iso()` 写入本地无偏移时间；`daily_coolpapers/exploration.py:82` 附近按 UTC 窗口使用 SQLite `julianday` 查询。

**修复建议与回归要求**：统一写入和查询的时间语义，并兼容既有无偏移数据。用真实入库格式覆盖窗口两端、当天排除、UTC+08:00 和明确偏移时间，保证显示日期与选样一致。

## F2：提取前未充分检查汇总上下文容量

**情况及触发条件**：提取模型上下文充足，但汇总 Prompt 绑定的模型上下文较小。预览与入队主要允许提取执行，无法及时反映汇总容量约束。

**复现步骤**：

1. 隔离库准备 20 篇论文，每篇原始摘要约 500 字符。
2. 提取 Profile 上下文设为 65,536；汇总 Prompt 单独绑定上下文为 2,600、输出预留为 2,000 的 Profile。
3. 经真实 `GET`／`POST /direction-exploration` 预览并提交生成。
4. 使用模拟模型响应执行 worker，检查请求、周报状态和论文消费状态。

**预期**：提取前检查汇总配置及容量约束，提前阻止明显不可执行的计划，或减少样本并明确展示实际可执行范围。

**实际**：预览显示 20 篇、2 批、3 次逻辑调用并允许入队；两次提取成功后，汇总在发出请求前报 `exploration_context_exceeded`。周报失败，20 篇已标记为消费，原配置快照下重试仍受同一限制。

**问题与影响**：用户在已经消耗提取请求后才得知计划无法汇总；成功提取论文随后不会作为全新探索样本重复进入。真实 Provider 下可能产生无可用周报的调用成本，本轮仅验证模拟请求，不代表已产生费用。

**定位线索**：`daily_coolpapers/exploration.py:161` 附近的计划构建与执行逻辑。

**修复建议与回归要求**：将汇总模型、输出预留及必要输入计入预检；运行时继续保留最终容量检查。覆盖提取与汇总采用不同 Profile、明显容量不足、边界容量，以及成功提取后的可恢复路径；明确区分已提取和已成功生成周报。

## F3：缺失热度与零值混淆，重抓后时间未同步更新

**情况及触发条件**：源站未提供点击计数时解析为 0；后续重抓更新计数，但探索使用的热度采集时间仍指向首次记录。

**复现步骤**：

1. 同类目、同源日期准备两篇论文：一篇缺少计数，另一篇明确 PDF/Kimi 点击均为 0。
2. 入库后生成探索计划，检查选样组、百分位和比较组大小。
3. 次日重抓第一篇，将计数从 0 更新为 10，再检查 `heat_captured_at`。

**预期**：缺失值不作为真实零参与热度优先选样，可进入随机池；热度时间应对应当前计数的采集时间。

**实际**：两篇均进入热度组，百分位均为 0.5，比较组大小为 2。计数更新后，`heat_captured_at` 仍为第一天。

**问题与影响**：未知数据伪装成已测量热度，影响比较组及抽样；时间字段无法解释当前计数的采集时点。此问题不只涉及无法反推的历史零值，也影响新采集数据。

**定位线索**：`daily_coolpapers/crawler.py:782` 附近的计数解析，`daily_coolpapers/db.py:1102` 附近的入库更新。

**修复建议与回归要求**：保留计数缺失语义，计数及其采集时间一致更新。覆盖缺失、明确零、正值、重复抓取及部分字段缺失；历史无法恢复的数据应明确标记，避免推断为真实零。

## F4：已有有效命中仍被归为分类待完成

**情况及触发条件**：存在多个启用方向，论文在其中一个方向已明确 `matched`，另一个方向暂无分类结果。

**复现步骤**：

1. 启用两个关注方向。
2. 为论文仅保存第一个方向的 `matched` 结果。
3. 检查现有方向判定为 `effective=True`，然后打开探索预览。

**预期**：既有命中已能确定有效聚合状态，应按 `matched` 处理，有资格进入边缘探索池；不保证最终一定抽中。

**实际**：计入“分类待完成”，直接排除出边缘样本候选。

**问题与影响**：探索聚合与现有有效方向语义不一致，减少已有方向边缘研究的覆盖。PRD 仅要求在缺失结果导致无法确定有效聚合状态时排除。

**定位线索**：`daily_coolpapers/exploration.py:115` 附近的分类聚合。

**修复建议与回归要求**：复用有效方向聚合规则，区分“结果不齐”与“无法确定状态”。覆盖已命中加缺失、全部缺失、失败结果以及人工覆写，确保不会错误纳入真正无法判定的论文。

## F5：重新汇总后候选 ID 指向另一候选

**情况及触发条件**：部分成功的周报再次保存汇总结果，模型返回相同候选但排列顺序发生变化。

**复现步骤**：

1. 在隔离库通过 `validate_synthesis` 和生产持久化函数保存部分成功周报，候选顺序为 Alpha、Beta。
2. 通过真实人工处理表单，将 ID 1 的 Alpha 设为“观察”。
3. 对同一周报，通过生产结果持久化函数保存模拟恢复汇总，顺序改为 Beta、Alpha。
4. 检查 ID、候选名称及观察状态。

**预期**：历史 `run_id + candidate_id` 始终对应同一候选，顺序调整不改变既有身份及引用含义。

**实际**：Alpha 保留观察状态，但变为 ID 2；原 ID 1 改为指向 Beta。

**问题与影响**：该复现中观察状态仍跟随原名称，不能据此断言状态被转移；但原候选 ID 的含义已改变，历史链接及基于 ID 的引用可能展示另一候选。

**定位线索**：`daily_coolpapers/exploration.py:244` 附近的候选 ID 分配，`daily_coolpapers/exploration_db.py:137` 附近的恢复保存。

**修复建议与回归要求**：候选持久身份不依赖输出排序；明确新增、替换和延续关系。覆盖重排、增删、改名、重复保存、已有人工处理与旧表单；补充完整恢复流程端到端验证。
